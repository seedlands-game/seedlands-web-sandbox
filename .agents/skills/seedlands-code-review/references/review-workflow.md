# 审阅工作流与报告模板

## 1. 解析并冻结输入

| 输入                     | 解析方式                                                              | 必须记录                                |
| ------------------------ | --------------------------------------------------------------------- | --------------------------------------- |
| `base...head` 或两个分支 | 验证 ref，求 merge-base，审阅 `merge-base -> head`                    | ref 名、两端 SHA、merge-base SHA        |
| 普通 commit              | 读取 commit 与父提交，审阅 `parent -> commit`                         | commit SHA、parent SHA                  |
| merge commit             | 展示所有父提交并要求明确比较父线；若用户已给 base 则按该 base         | merge SHA、父 SHA、选定基线             |
| PR URL/编号              | 用可用 GitHub 能力 live read metadata、base/head SHA、文件列表和 diff | URL/编号、base/head、读取时间、当前状态 |

先检查目标对象是否存在、diff 是否可读取、工作区是否有未纳入的改动。远端分支或 PR 的可变名称不能替代 SHA。若目标 SHA 在审阅中变化，当前报告继续绑定旧 SHA，并提示需要新 review；不要把两个版本静默拼接。

受改文件和关键邻接代码一律从冻结 head tree 读取，例如 `git show <head-sha>:<path>`、等价 Git object API 或隔离的 exact-SHA worktree。不得用当前 checkout 的同名文件替代。审阅合同基线从 frozen base tree 的 `AGENTS.md`、长期 docs 和已接受 spec 取得；head 新增或修改的合同作为待审内容单独比较，不能给自己豁免。

生成变更清单：文件状态、增删行、生成文件/二进制/重命名、相关 spec 与测试。生成文件可抽样验证来源，但人写逻辑要逐文件覆盖。大 diff 先按可独立能力和风险分批，保留 coverage ledger；无法在本轮覆盖完整时明确停止位置，不用“看起来没问题”补齐。

## 2. 分层理解

先找承载主要行为的入口，不从按字母排序的第一个文件开始。每个逻辑切片依次回答：

1. 为什么变：从 spec、PR 描述和代码分别得到什么；不一致时保留冲突。
2. 入口与消费者：谁调用、谁读取结果、最终可观察行为是什么。
3. 数据与状态：输入、转换、权威 owner、epoch/revision、缓存和持久化如何变化。
4. 时序与生命周期：启动、正常、取消、重入、失败、销毁路径是否闭合。
5. 兼容与回退：旧数据/协议/调用方如何处理，fallback 是否沿既有反馈链路。

把“diff 直接显示”“从邻接源码确认”“从测试确认”“推断”“未知”分开。不要用作者描述证明实现正确，也不要用运行测试反推未覆盖的设计合同。

## 3. 阅读报告

建议结构：

```markdown
# <change> 代码阅读与独立审阅报告

## Review identity 与范围

## 一句话结果与风险热点

## 变更分层

### 逻辑切片 A

### 逻辑切片 B

## 推荐阅读顺序

## 流程或时序图（仅在有帮助时）

## Diff codemap

## 测试与证据边界

## 待确认问题（如有）

## 人类复核建议

## 独立审阅 Findings
```

### Diff codemap

Codemap 至少记录：

| 路径 / 符号 | 变更角色 | 上游入口 | 下游/副作用 | 状态 owner | 相关不变量 | 人类审阅重点 |
| ----------- | -------- | -------- | ----------- | ---------- | ---------- | ------------ |

只纳入变更文件和理解它们必需的邻接节点。对重命名区分移动与逻辑变化；对删除说明消费者是否同步移除；对测试说明它证明的行为，不只写测试名。

### 图示选择

- 三个以上依赖步骤：流程图。
- 跨线程、Worker、网络、异步回调或持久化顺序：时序图。
- owner/模块嵌套：小型关系图或表格。
- 单函数局部变化：不画图。

图中的节点名须能映射到真实符号或模块；用箭头标签写关键数据、消息或状态，不把推断画成事实。

## 4. 独立审阅

先做设计/权威/状态所有权检查，再逐文件检查正确性、边界、并发、错误和测试。最后核对所有新增调用方、所有消费者、所有失败出口、所有资源释放和所有 changed file 已进入 coverage ledger。

Finding 模板：

```markdown
### [P1] 迟到结果会覆盖新 revision

- 位置：`path/to/file.ts:123`
- 触发：旧任务在新 epoch 已提交后返回。
- 影响：客户端缓存回退到过期世界状态。
- 规则：STATE-01。
- 证据：调用链与缺失的 revision gate；相关测试只覆盖顺序完成。
- 建议：在 owner 的提交边界按 epoch/revision 拒绝旧结果，并补乱序用例。
- 置信度：高。
```

置信度只描述证据完备性，不降低严重度。无法证明触发或影响时，移到“待确认问题”。P2 不能只表达个人风格；写不出具体维护成本或可读性影响时删除。

## 5. 覆盖与交接

测试、CI、日志和运行报告必须绑定 exact head SHA；无可靠来源写 `NOT_AVAILABLE`，没有执行写 `NOT_RUN`，不要把相邻提交或当前 checkout 的绿色结果移植过来。任务允许本地执行时，在隔离的 exact-SHA checkout 运行相关命令；任务禁止本地写入或环境不具备时只记录缺口。

在 Findings 前给人类 1–3 个建议亲自核对位置，优先选择权威提交点、跨边界时序和自动化证据无法覆盖的用户体验。报告末尾 findings 后不要再追加可能掩盖问题的长总结；只可在该章节末行附 coverage 状态：`完整 / 部分（缺口）`。
