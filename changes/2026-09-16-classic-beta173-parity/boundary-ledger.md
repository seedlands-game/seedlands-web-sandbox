# Classic 分层门禁与改动台账 v0.1

状态：**规划规则；当前没有 Classic 实施改动**。本台账只约束本次 b1.7.3 单人玩法对照，不改写 Kernel/stdlib/Playbook 的长期职责定义；职责基线见[可组合玩法架构](../../docs/composable-gameplay-architecture.md)。每阶段先记预计改动，实施后按真实文件 diff、测试和验收证据回填。文档本身的修订不算已实施玩法。

## 分类与处理

| 标签                               | 命中条件                                                                             | 处理                                                                                     | 是否需新增用户审批       |
| ---------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------ |
| `ERROR-kernel`                     | 改 `packages/kernel/**`；或改其他目录却实质改变 Kernel 的公共合同/不可绕过不变量     | **停止该路径**，只读取证并形成缺陷/方案报告；批准前不做 Kernel RED/实现/迁移，更不能绕过 | **是，单独审批精确方案** |
| `WARNING-stdlib`                   | 改 `packages/stdlib/**` 的机制、默认实现、公开适配或测试；Classic 需求暴露基础库缺口 | 记录原因、范围、调用方、状态 owner、测试和影响；在已有 SDD/Breaking 规则下实施           | 分类本身不新增审批       |
| `NORMAL-playbook`                  | 改 `playbooks/classic/**` 的内容、参数、规则、模块声明与组装                         | 按内容/机制逐项实现和验收                                                                | 分类本身不新增审批       |
| `CLIENT/ENGINEERING`（非三档评级） | `apps/web/**`、原创资源、Harness/CI、文档等                                          | 按实际 owner 和项目治理另记；不能用于掩盖 Kernel/stdlib 合同变更                         | 由既有变更类型决定       |

“需要修改 Kernel”是 `ERROR` 的**停工与复核信号**，不以文件路径或有限枚举本身自动证明过去设计有缺陷。报告必须用可复现消费者证明：某项所有合法玩法共同需要的保证，现有公开合同确实无法提供；若只是 Classic 特有规则、标准模块缺失或客户端表现缺口，分别回退到 Playbook、stdlib 或 Web。反过来，不能为了维持表面零 Kernel diff，把真正的权威缺陷复制到 stdlib、Playbook 或客户端。

## `ERROR-kernel` 审批报告的必填合同

每个候选独立编号 `K-###`，在任何 Kernel 写入前记录：

1. **先前缺陷**：现行 Kernel 版本/代码位置、预期的玩法无关不变量、最小合法消费者、可复现失败或静态反例；区分“证实缺陷”“仅疑似缺口”和“误判”。
2. **本次需求**：对应 [inventory](inventory.md) 方块/实体/配方或 [mechanics](mechanics.md) 机制编号、b1.7.3 原版行为证据、为什么这不是 Classic 专属规则。
3. **拟改方案与理由**：最小 Kernel 改动、公共 API/状态/时序变化；复用现有合同、Playbook、stdlib 薄扩展等备选为何不能满足，证据是什么。
4. **影响**：其他合法世界、模组、存档/协议兼容、确定性、权限和性能；迁移/失败回滚方案；跨 owner 与公开入口影响。
5. **验证与审批**：实施前 RED/反例设计、通过门槛、spec/hash、用户对精确方案的批准记录。获批后单独 change 实施，回填实际 diff、GREEN 与产品证据；不能把批准视为自动发布/合并。

报告模板：`K-### | 状态 | 旧不变量与失败证据 | Classic 需求/机制 ID | 备选 | 最小方案与理由 | 影响/迁移 | RED/验收 | 审批引用 | 实际 SHA/diff`。没有证据或审批时保持 `BLOCKED`，不填“已修复”。

## 每个工作单元的改动登记字段

`ID | 阶段 | 需求/机制编号 | 预计 owner/文件 | 实际文件/公开合同 | 分类 | 既有能力/缺口证据 | 方案/理由 | RED 与验收 | 状态 | 审批引用（如 K） | SHA/差异`。

- 同一机制若改三层，登记三行；测试、生成资源和 Web 适配也单列。预估与实际分开，文件路径不够时记录被改变的公共语义。
- `WARNING-stdlib` 至少写清为什么现有标准能力不够、为何扩展是可复用机制而非 Beta 常量、它的状态与行为测试归属；不把“Stdlib 预期会改”当作免于记录的理由。
- `NORMAL-playbook` 绑定内容行或机制参数；禁止在局部 Playbook 另建不受 Kernel 授权/事务/存档约束的权威状态。
- 阶段结束检查实际 diff 中 `packages/kernel/**` 是否为空，核对 stdlib/Playbook/Web 项与台账覆盖率；发现未登记变化先暂停交付、补证与分类，不能事后把 ERROR 降级为 WARNING。
