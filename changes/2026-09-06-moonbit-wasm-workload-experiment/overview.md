# 方案概述：让实测决定哪些计算进入 Wasm

建议批准这条实验路线：**优先 MoonBit，保留现有多 Worker 架构，逐项验证，最后只保留能改善完整游戏工作负载的项目。** 目前已经完成调研和合同，没有声称取得任何 Wasm 性能收益。

## 为什么优先尝试 MoonBit

MoonBit官方提供独立Wasm产物、数值类型、导入导出及统一构建/测试工具链，具备本项目做计算内核的基础。当前文档/发行仍处于0.x版本，稳定ABI、工具链固定和数值一致性需要先验证。因此首选是有条件的：用网格、生成、流体三类代表计算对照Rust；端到端几何平均差距≤10%、单项≤20%，且没有能力阻断，就遵循你的偏好选择MoonBit。

默认用线性内存Wasm，WasmGC留作小型对照。项目主要处理体素与网格数值缓冲，批量读写是否高效比语法是否相近更重要。详细依据和官方来源见[语言与线程调研](research.md)。

## 怎么防止“内核更快，游戏更慢”

1. 先测当前TS的全部CPU责任、A/A噪声、复制与排队成本。预估收益覆盖不了新增边界成本2倍的项目，标注不迁移。
2. 分项保留门槛：端到端p50改善≥15%、95%置信区间下界>0，同时有足够绝对收益（每任务≥0.2ms，或持续≥1ms CPU/秒；启动/地图≥20ms），并守住尾延迟、工具链与维护预算。
3. 同算法、同数据、同Worker数量比较。地图另外比较TS Worker，算法/布局优化另外给TS控制组，防止把搬线程或换算法收益算成Wasm收益。
4. 所有分项通过项一起开启，与最新原始TS做统一A/B。按场景报告启动、跨Chunk、编辑至真实显示、物理、AI、地图、存档、帧p95/p99、CPU和内存。组合不合算就做消融，允许最终一项也不迁移。

本地实际headed Chrome、1920×1080、同画质和内部尺寸作为主性能环境；10对平衡AB/BA，保留冷启动、异常和原始记录。跨语言字节/世界/物理行为先一致再计时。所有阈值及用例设计见[A/B评测合同](ab-plan.md)。

## 线程安排

维持目前默认5个后台Worker：Authority、Logic、Fluid、General、Persistence各1个，另外对照6Worker配置。每个有收益计算的Worker持有自己的单线程Wasm实例与独立内存，**实例不会再启动一个Wasm线程**。默认不开共享内存或Wasm多线程，也不改变部署响应头。

特殊情况有两项：物理在Authority原地调用，不能每tick往返计算池；地图可搬入General低优先级任务，但必须通过TS Worker控制组证明Wasm的额外价值。本地预测保持同一数值合同，小批量不强行Wasm化。
