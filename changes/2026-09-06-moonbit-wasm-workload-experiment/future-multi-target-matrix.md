# 长期背景：多运行环境评测草案

**不属于当前实施、验收或成本承诺。** 用户最新澄清：当前不开发Node Dedicated Server、Node pool或Rust Node-API，先完成Rust-first浏览器Wasm实验。下文保存为未来可复用思路，不能据此扩大当前scope。

# 两个长期产品环境的评测合同

本版替代 `faa719f` 中的仅浏览器 MoonBit 优先矩阵。浏览器 Integrated Server 和 Node Dedicated Server 分别决策；native 只提供上限证据，不替代任一产品验收。现有短测和旧 corpus 数据保留为诊断，不混入新矩阵。全部浏览器任务 headless。

## 先固定变量，再扩大并发

比较分三层，结果分别报告，禁止合并归因：

1. **核心与边界层**：同机器、固定单工作线程、相同算法与布局、同 corpus、同批大小，分别量纯核心、语言边界、输入准备与输出转化。浏览器 TS 主线程只在 kernel harness 中作单线程参照，不把整个现有五 Worker 产品重写为单线程。
2. **调度与并发层**：TS 原版与同布局 TS 分开，固定 pool=1，然后 2/4/最多可用核数。Node TS、Rust Wasm、Rust Node-API 同池大小；浏览器 Web Worker 各自独立 Wasm。只改变调度位置时不得同时更换算法。
3. **真实集成层**：浏览器实际五 Worker Integrated Server 与 Node 现有 TS Authority 编排各自 A/A′/B。浏览器是当前真实产品门禁；Node目前是HeadlessSession代理门禁，不能替代未来网络Dedicated Server的产品A/B。仅加入本环境有消费者的通过项，不比较两个环境的绝对帧率或宣称 Node 比 Chrome 必然更快。

跨 Node/Chrome 的 V8 版本、flags、渲染竞争和宿主 API 分别记录。另设无渲染浏览器 kernel harness 与 Node 相同 kernel harness 的 TS 对照；产品有/无渲染竞争的差异只作环境效应，不作为语言选型结论。

## 明确矩阵

| 环境/变体 | 执行与产物                       | 必须保持一致的对照                                            |
| --------- | -------------------------------- | ------------------------------------------------------------- |
| 浏览器 B0 | TS 单线程 kernel harness         | 与 B1 同算法/布局/corpus；测搬线程总成本                      |
| 浏览器 B1 | TS Web Worker                    | 原 TS 与同布局 TS 两条，现有产品 TS Worker 是正式基线         |
| 浏览器 B2 | 已完成 MoonBit Wasm + Web Worker | 同一池大小、批量ABI、传输策略；不新扩服务端 MoonBit           |
| 浏览器 B3 | Rust Wasm + Web Worker           | Rust core 同提交/功能集合；与 B2 完整准备/输出等价            |
| 浏览器 B4 | 本环境正收益集统一 A/A′/B        | A 冻结原 TS；A′新适配全关；B按内核选择已通过产物              |
| Node N0   | TS 单线程                        | 原 TS 与同布局 TS，两者不混为一个基线                         |
| Node N1   | TS worker_threads pool           | N=1先归因调度，再固定N扩展                                    |
| Node N2   | Rust Wasm，运行于 Node worker    | 与N1同pool、数值包、缓存/工作区重用                           |
| Node N3   | Rust Node-API                    | 单线程边界probe；产品在与N1相同pool内同步调用                 |
| Node N4   | Rust native standalone           | 同core/数据/算法，报告纯计算上限；不拿无IPC计时冒充Node端到端 |
| Node N5   | 本环境正收益集统一 A/A′/B        | 同一TS Authority、世界/命令轨迹、频率/提交规则                |

单工作线程 language probe 固定为同一个pool=1 Worker内的N1-TS/N2-Wasm/N3-Node-API，使用相同clone/transfer和排队策略；N0→N1只说明搬线程。若另作主线程probe，则三语言全部在主线程同布局执行并单列。native 测量不含进程启动/文件解析的核心段和含这些项的工具总成本两个值。多进程独立世界分片是单独拓扑实验：固定总计算线程、相同总世界数、显式记录IPC。它不阻塞三内核 MVP，不引入跨分片事务或完整 Rust world server。

## 输入、正确性与可比性

统一 corpus schema、seed、generatorVersion、任务序列和 SHA-256。W02 宏观上下文预备保留 TS，两种语言使用同一列输入，报告 TS 准备在端到端中的比例；native 单独跑填充不能宣称整体生成速度。

首组 W07 含 4/5 Chunk、128 frontier+64 cleanup，平均数值输入约465KB；冷/稳态、稀疏/密集、未知邻块、跨边界和顺序事务均覆盖。W14 包含无修改、稀疏、稠密 diff、palette/raw tie、fluid sidecar；W15 CRC 独立计时与共驻收益分开。W04/W05是一个mesh描述符单元的两类场景，生产采用需共同过关，收益不能相加。

预置语料与路径哈希之外，测量前做强等价（数组字节/索引顺序、float bits、保存字段、候选/read-set/有序写入）。每次性能运行检查摘要、请求产物身份、无fallback/trap和输入未改写。增大并发不能改变输入分片或丢任务；采样失败必须保留。

## 指标与计时边界

每个预注册的必跑cell记录下列指标；不执行所有维度的笛卡尔积，稀疏cell清单见后文：

| 指标           | 操作定义与限制                                                                                                                                                                                                                                                                   |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 核心计算       | 核心函数入口至返回；工作区已准备，输出仍是核心格式。JS高频细调用不可代替批量入口                                                                                                                                                                                                 |
| 调用/边界      | adapter入口、marshal完成、core开始/结束、unmarshal完成时间戳；空批量/no-op量固定成本；扣减后的残差只能叫估算，不能伪称精确纯FFI                                                                                                                                                  |
| 端到端         | 从构造/复制本次输入起，含序列化/传输/排队/计算/输出回传及宿主转换，结束于调用方拿到可消费结果                                                                                                                                                                                    |
| 复制与内存增长 | 双向bytes、clone/transfer次数、分配/增长次数及增量、scratch峰值；首次增长与稳定复用分别报告，不把准备移到计时外隐去                                                                                                                                                              |
| 延迟/吞吐      | p50/p95/p99、tasks/s与每任务输入量；固定总任务量的完工时间，固定时间饱和吞吐作为另一组                                                                                                                                                                                           |
| 多线程效率     | S(N)=T(1)/T(N)，E(N)=S(N)/N；注明实际OS线程数和隐藏运行时线程、过量订阅、CPU型号                                                                                                                                                                                                 |
| RSS/GC         | Node记录进程RSS一次而非按worker重复累加，worker heapUsed/heapTotal、external、arrayBuffers独列；GC事件/暂停与event-loop delay按进程/worker采集。浏览器按独立profile进程树归属记录RSS、CDP heap和GC可观察项，不能把linear memory当总RSS；缺指标用UNSUPPORTED/NOT_COLLECTED，不填0 |
| 启动           | 进程/Worker启动、模块读取、compile/instantiate或dlopen、首次调用、稳定调用分别记录。冷启动使用新进程/context，HTTP/OS缓存状态声明，不能仅刷新页面自称磁盘冷态                                                                                                                    |
| 体积/发布      | Wasm/raw+gzip、JS glue、各target `.node`/native体积、依赖/下载与构建时间；记录OS/arch/libc、Node-API版本、工具链/flags/hash                                                                                                                                                      |
| 产品           | 浏览器 ready、activeCPU、帧/physics尾延迟、流体可见、加载/保存等；Node authority推进时间、command/候选延迟、提交有效率、吞吐、event-loop delay与RSS                                                                                                                              |

Node高精度计时用 monotonic hrtime；浏览器非隔离环境时钟精度受限，极小核心用等量批次取平均并报告测量分辨率。不得用时钟量化导致的0宣称无限加速。native内部时间与JS外层端到端分别记录。

## 样本与统计

- 先每个正式主场景做6个A/A完整配对校准；现有P0仅是6场景各1对，保留为探索性噪声证据，不能冒充每场景6对。
- 正式比较10个运行配对/平衡block，每次预热至少5秒或20任务中较长者。同一工作负载变体顺序平衡，不并发跑其他性能实验；记录外部资源争用，超噪声则增加样本或判不确定。
- 原计划每run30任务只够中位数/尾部分辨率有限。新矩阵延迟分布每run至少1000任务，昂贵任务按预注册总时长给出不足原因；p99样本不足不作为保留证据，不能插值30个事件就宣称可靠p99。产品自然输入至少30秒，流体用户事件30次仍只用于该run的p95，跨run是统计单位。
- 以完整run/block为独立单位，10,000次paired bootstrap，给95%CI、p50/p95/p99绝对值与百分比；同一run中的帧和1000任务不是1000个独立实验。固定随机种子、balanced订单与全部raw可追溯。
- 冷启动另做10对并报告环境缓存状态；回收/失败/未知内存数据不选择性删除。正式结果引用source+未提交tree+产物+corpus+runner hash；对变化后的binary重新测量。

## 准入与止损门槛

维护前筛选保留旧绝对收益依据，但重新计入跨目标复用：单任务预计节省≥0.2ms，或持续≥1ms CPU/秒；启动/地图≥20ms，且计算节省>新增边界成本2倍。未来假设消费者不能算已实现收益。

分项正式采用需满足：相对当前本环境产品TS基线端到端p50改善≥15%，配对95%CI下界>0，同布局TS控制仍有可辨语言增益；若语言增益未过而布局增益明显，可只保留TS布局优化。p95/p99不能出现超噪声和预置容差的退化。小规模负收益需以实测交叉点按批量门限回退，不强迫全部任务都走Rust。

浏览器统一 A/A′/B 保留原主门槛：至少一项预注册产品主要指标改善≥10%、95%CI下界>0；frame p95/p99容差max(0.5ms,5%)，physics max(0.1ms,5%)，交互/任务max(2ms,5%)。Node统一以完成同一确定性trace的端到端时间或同负载吞吐为预注册主指标，改善≥10%、CI下界>0；authority/command p95/p99容差max(1ms,5%)，event-loop delay不突破预先记录的产品预算。不允许看到结果后换主指标。

浏览器保持单实例linear memory≤32MiB、5 Worker配置合计≤96MiB、新增压缩Wasm/glue≤150KiB，额外冷启动≤max(50ms,原值5%)、稳态60s可摊销；独立压力池按并发数另报，不混入产品预算。Node在MVP校准后冻结每worker scratch与RSS预算，再执行正式实验；上线默认需要预算已明确，不能以“native内存便宜”略过。默认仅一层并行，线程扩展非正收益即停止加线程。

MoonBit 浏览器专用实现额外记录与 Rust/TS 双实现的修复、发布、确定性和工具链成本；性能/体积/开发效率优势必须有实际数据，不能仅因已投入而保留。共享Rust核心的维护收益按当前两个实际消费者计算，不以完整Rust server的遥远预期覆盖当前负收益。

## 产物与平台门槛

MVP首先在本机macOS arm64验证全部三产物，确认Node实际版本和Node-API capability。正式计划包含Linux x64 GNU、Linux arm64 GNU、macOS arm64/x64、Windows x64以及Node22/24/26的构建/加载/等价矩阵；是否声明支持取决于实际CI/设备证据，不能用交叉编译成功替代运行测试。musl、其他arch另列不支持/待支持，不静默回退发布包。

CI按crate与产物分别构建/测试，发布物有manifest与可重现源码，平台缺包有明确TS或已验证Wasm回退。native `target-cpu=native`/SIMD优化只在标明宿主ISA的上限组，baseline portable构建不启用隐藏优化。发布流程本次只设计和本地验证，不外发npm包或部署。

## 预注册稀疏矩阵与投入上限

首阶段只冻结三共享内核族W02/W07/W14（W15为共驻依赖及单独microprobe）；浏览器专用W03/W04-W05/W06保留已有对照，待第一阶段门槛通过再分项，不新增MoonBit算法。

1. 核心层：每族只固定一个生产代表批量和相同布局，浏览器B0/B1/B2/B3、Node pool=1的N1/N2/N3加N0调度参照与N4原生上限；每族自然/压力两个固定corpus分层，极端正确性case不按等权混入性能分布。
2. 规模层：只给通过核心层的backend增加小/中/大三个预定批量；记录交叉点。并发只测pool=1/2/4（可用核不足则明确N/A），输入总量固定，算法/布局不再扫描。
3. 集成层：每环境只运行一组预注册正收益集合与A/A′/B；browser固定生产5Worker。Node代理固定1会话与4会话两个分层，并保持相同总pool大小；新增网络Dedicated产品组等待真实消费者能力，不伪造。

所有cell在首个正式样本之前写入机器可读matrix manifest，记录主指标、场景、批量、线程数、seed、样本数、门槛和排除原因并hash。探索阶段可减少样本做可行性；正式固定10配对/足够p99任务。探索样本不复用作确认集；多候选置信结论做Holm校正或使用独立确认集，最终采用必须有独立组合验证，避免挑好看的cell。

## 维护账本与正式native工具

采用决策统一按未来12个月、每季度一次发布、每内核两次规则/错误修复的固定情景估算，并另列实际工时与假设。分别计core一份算法、Wasm/NAPI/native三个adapter的构建/平台验证、MoonBit第二算法实现的同步/等价和工具链升级，不把已经花掉的成本作为继续理由。

第一MVP完成后设预算：每次共享算法修复，三个adapter的额外适配+跨产物等价维护合计不超过1工程日；MoonBit浏览器专用实现另外不超过0.5工程日/次修复、12个月新增维护不超过4工程日。超出预算必须重新评估范围，不能静默扩大长期支持。Moon保留至少满足一个可验证收益：相对最佳Rust/TS端到端再改善≥15%且CI>0；或gzip减小≥30%且端到端/冷启动无超5%退化；或同合同实际开发+修复工时节约≥30%且覆盖全年额外维护。开发优势未实测则标证据不足。绝对收益门槛和产品组合门槛仍同时生效，不能因小文件比例大就保留。

native正式工具验收：版本化输入corpus/存档记录文件，经同Rust core输出逐字节等价结果或明确错误码，支持结果校验与benchmark两个用途；非法/截断输入、不同schema、重复调用、只读输入保护、可重复构建/版本查询均需CLI E2E。没有CLI旅程/发布manifest就不能称native工具产物准出。native服务进程和网络协议保持非目标。
