# 计算队列与池复查

## 合同与测试设计

落实 A12 的有限队列、依赖、取消、公平推进和生命周期。队列已有任务数/字节限制，但未实现优先级老化，完成任务集合永久增长，失败/取消依赖会永久留队，重复任务 ID 可破坏字节计数；池关闭未回告排队任务，关闭后切 epoch 还会重新创建 Worker。

先新增确定性 RED：持续交互工作下后台任务有限派发内进展、重复 ID 与未知依赖拒绝、有限完成历史而已排队依赖不丢失、失败依赖级联释放、实际池故障/取消回告、关闭后无任务或 Worker 复活。另补已有依赖时禁止错误合并旧 revision。

## RED 记录

- 队列 9 项中原有 5 项通过、新增 4 项失败：后台任务饥饿、重复 ID 被接纳、100 次完成后过期依赖仍被接纳、缺失失败传播端口。
- 池 9 项中原有 7 项通过、新增 2 项失败：子任务没有失败回执；关闭只回告运行任务而漏掉排队任务。

## 实现

- 每个 lane 按实际派发次数老化，每等待 8 次派发提升一级优先级，同分按任务 ID。后台任务不因持续交互无限饥饿；合并保留原等待年龄。
- 同一 epoch 的任务 ID 单调递增；重试需分配新 ID。重复/过期 ID、未知/已淘汰依赖、无效 priority/category/预算显式拒绝。已有生产计算运行时使用统一递增序列。
- 完成历史至多为队列容量的四倍；接纳/完成时把已经满足的依赖从待执行任务中消去，因此历史淘汰不破坏已排队工作。运行记录至多三个，与本次计算池硬上限一致。
- 有子任务引用旧 revision 时保留旧任务，不用新 revision 冒充旧依赖；失败/取消按依赖链释放并逐个通知失败。
- 池关闭回告所有排队和运行任务并清空队列；关闭后切换 epoch 不得重建 Worker。

## 证据与剩余边界

定向队列、计算池、浏览器计算运行时测试全部通过（最终数量见执行输出）；相关文件 Prettier/ESLint 通过。完整 source/test TypeScript 检查当时因主线替换 `World.server` 为 Authority 端口及已有测试 DTO 的并行迁移失败，不记录为整体通过。

这些只证明计算池层。`MeshTaskScheduler` 入池之前的优先级与故障释放也必须闭环；不能以池层老化代替完整 streaming 公平性。实际 2/3 Worker 浏览器性能和故障旅程仍待准出。
