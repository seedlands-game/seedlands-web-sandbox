# 仓库导航与目录组织规范

## 背景与目标

用户难以从大量平铺文件定位代码。建立当前代码地图、按问题查找的入口和后续文件归属规范，使新会话能理解运行链路并定位实现与验证。

## 范围与非目标

本次采用 Agile 文档流程：新增代码地图、目录规范，更新 README 与 AGENTS 的导航及过时的职责摘要。既有长期对齐文档已通过本地合并接入本分支。

不移动生产代码、不调整导入或可执行架构边界、不修改测试口径、不重写历史 change。候选目录分组只作为后续迁移建议，不表示已实施。跨模块重构须另建 Breaking spec 并按现有流程审核。

## 决策

- 当前地图以生产代码基线 `f245493` 为准，区分运行调用、消息通信与类型引用，避免把文件夹名当作完整依赖保证。
- 分开维护 `docs/code-map.md`（代码在哪里）与 `docs/repository-structure.md`（文件如何归属），长期目标仍由已有对齐文档承载。
- 新文件组织约定属于文档指导；现有 ESLint、命名配置才是机器执行的规则。本次不声称新增自动门禁。

## 行为

- 给定首次阅读者，当从 README 进入代码地图时，能找到启动、权威状态、输入物理、计算渲染和存档的真实路径。
- 给定新增文件，当阅读目录规范时，能区分平台适配、领域逻辑、协议和验证证据的归属，并识别尚未落地的目录建议。
- 给定历史 spec 与当前源码存在路径差异时，以当前地图导航实现，历史合同保持原样。

文档变更没有可执行产品行为，产品 RED 不适用。修改前已确认缺少上述两份导航文档；可观察的完成态为入口可发现、链接落地、现状与建议分开且提交只涉及文档。
