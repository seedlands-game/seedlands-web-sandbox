# SIMD 分项与组合 A/B

## 结论

2026-09-06 至 09-07 的最终 headless Chrome 正式运行 **7/7 通过**，耗时 48.4 分钟；run id 为 `2026-09-06T15-46-01-056Z`。每场景 10 对、每模式 1,000 任务、5 秒预热，共 210,000 个测量任务；独立统计单位仍为每场景 10 对 run。

四种 Rust SIMD 内核都已实现并通过强等价：occupancy 热内核耗时下降 **80.5%**，UV **15.1–19.2%**，颜色 **79.4%**，索引 **53.0%**。这证明内核有加速潜力，并不等于产品帧率提升。

UV/颜色/索引组合后，混合网格与压力网格在 Worker 内完整打包阶段的平均耗时分别下降 **19.4% / 22.6%**，对应 **0.0473 / 0.1216 ms**；带额外准备与往返的独立任务平均耗时分别下降 **7.7% / 4.6%**。组合 p50 均未达到预注册门槛；颜色/索引单项还有 p95 退化。本轮没有通过全部产品采用条件的项，**保留 SIMD 候选代码和标量对照，不引入产品 loader，不改变默认 Wasm 开关**。这不表示浏览器 Wasm 或 Rust SIMD 没有长期价值；下一步先减少已有复制，再在真实生产消费者中复测。

当前没有独立 Worker RSS/GC 证据，也没有正式整游戏旧版/新版 A/B，因此不对尾延迟原因或游戏帧率作额外推断。预制 mesh 的输入投送是 harness 的额外边界，不能把该外围请求延迟当作生产 W06 的精确耗时。

## 比较方法

- 同一 Chrome、同一 CPU、一个无头浏览器 Web Worker；所有实例独立线性内存，关闭 Wasm threads、relaxed SIMD 和自动向量化，无跨源隔离。
- Rust 标量与 SIMD 使用同一源码算法、输入/输出偏移、18 MiB 初始内存、32 MiB 上限和 LTO 设置。各实例复用固定 16 MiB arena，测量期间不 grow。SIMD 仅改变规则性位操作与 lane 批次。
- 每个场景 10 对平衡顺序，单模式预热至少 5 秒，每 run 1,000 个完整任务。按 run 成对 bootstrap（10,000 次、固定随机种子），不把 10,000 个任务冒充 10,000 个独立实验。
- 全任务时间从调用者 `structuredClone` 输入开始，到 Worker 结果交付为止；包括准备、入队、transfer、Wasm 入/出复制、调用与回传。这里是独立 Worker 服务延迟，不是游戏帧时间。生产 W06 在 `world-kernel-adapter.ts` 中消费同一 Worker 刚生成的 mesh，不存在本 harness 为投送预制 mesh 而增加的整份输入传输；因此同时报告 Worker 内完整打包阶段，不能用这个外围请求延迟单独推断生产 W06 的精确占比。每次结果 hash 在计时结束后校验；强等价边界由独立 Vitest 补充。
- 单核时间先把输入放入 Wasm，再重复同一 kernel 至至少 100 次/约 1,677 万个元素，取每次均值以避开粗时钟。该结果是热内存内核耗时，仍包含数值 ABI 调用，不能替代全任务指标，也不能直接与全任务相减作为精确复制成本。
- occupancy 为 32³ 格；UV 有 32,768 与 262,144 个元素；RGBA/索引为 262,144 个元素。UV raw corpus 覆盖广泛位模式，包括非正常 UV，只用于同算法受控筛选。真实网格输入中的 UV 在组合场景另测。
- `mesh-natural` 文件名沿用 harness，但实际是父 change 的 **30 组混合/边界网格 corpus**，包含自然地形、空/实体、编辑和高面数案例，并非用户真实游玩的抽样频率。`mesh-stress` 是 6 层棋盘体素经生产 `meshChunk` 得到的高面数网格。两组都同时启用 UV、颜色和索引 SIMD，是 W06 内三项的组合 A/B。

## TS 控制组与正确性

网格的原 `batchMeshData` / `compactMeshData` 使用大数组展开，部分输入触发调用栈上限。报告保留 `legacyFailures` 编号，不把失败当作慢运行。可执行的原 TS 条目与 staged control 结果逐一核对；其余条目的 oracle 是数值规则相同的 staged TS arena control。

网格正式比较以 Rust scalar / SIMD 为主，它们的全部布局、复制和内存容量相同。staged TS 与 Rust 的数据偏移/控制路径一致，但 staged 只有 16 MiB memory，Rust 为 18 MiB；不得把这个附加对照说成完全相同的宿主内存占用，更不能称其为“旧 TS 游戏版本”。该对照只使用合法、互不重叠的输入区间；Rust 无效 ABI 负例由 Vitest 验证，staged control 没有完整镜像其拒绝规则。

新 Rust 索引导出用 `f64` 精确返回整个 `u32` 最大值范围，`-1` 专用于错误。JS `number` 可以精确表示全部 `u32`；core 内仍是 `u32` wrapping 加法和无符号 max。这样避免旧 signed-i32 ABI 将高位最大值误判为错误，生产 `MeshPackKernel` wrapper 的高位数值测试覆盖该边界。

## 内存与构建成本

Rust core 没有宿主依赖。适配层固定低地址 arena，由 linker shim 去掉 rustc 隐式 `--stack-first`，令 data 从 16 MiB 开始，后接独立 1 MiB 栈。导出的 `__data_end` / `__stack_pointer` / `__heap_base` 由测试检查，整 arena 写满后仍运行强等价；不再借用预留栈空间。

每个 Rust 实例初始 18 MiB，标量与 SIMD 相同。benchmark 同时持有两个 Rust 实例，网格还持有 16 MiB staged 实例（合计 52 MiB 线性内存）；此共存只是便于公平轮换，不能拿某模式记录的 18 MiB 声称整个 Worker 的 RSS。报告中的 `computeMs` 包括 Worker 内的打包/分组以及 Wasm 输入输出复制；这些阶段未独立拆出到低于时钟分辨率的边界时间。实际 GC 和独立 Worker RSS 标记 `NOT_COLLECTED`，没有填写 0。初始化记录包含本机 fetch/编译/实例化，非独立进程冷启动分布。

构建新增固定 Rust 工具链、Wasm target、两次 Cargo release 编译、一个小型 linker shim 与 ABI/源码 hash 检查；普通 Rust 边界测试需要 Cargo。当前只验证 macOS arm64 与本机 Chrome，Windows linker 启动方式及多平台发布尚未验证。没有新增 Node Dedicated Server、Node-API 或 GPU 依赖。

## 门槛与结论解释

采用须同时满足完整任务 p50 至少改善 15%、95% CI 下界大于 0、p95/p99 不超过 `max(0.05 ms, 5%)` 退化，并在真实消费粒度节省至少 0.2 ms/任务或可证明 1 ms CPU/秒。任意一组的 p50 落到 0，指标标记 `BELOW_TIMER_RESOLUTION`，不能报 100% 改善，也不能据此启用。平均全任务时间可辅助解释，但不事后取代预先约定的 p50 采用门槛。

SIMD 能力探测和标量回退属于产品采用的前置条件；本实验 harness 显式要求支持 SIMD 的浏览器，故不会伪装 fallback 为 SIMD 样本。若候选不满足产品门槛，不新增生产 loader，也不改变现有默认关闭的 Wasm 产品开关。

## 复现与原始证据

`package.json` 提供 `wasm:simd:build`、`wasm:simd:ab`、`wasm:simd:report` 和 `rust:check`。报告命令只接受同一 run id 下完整的 7 项正式结果，拒绝 smoke、缺项和非预期旧 TS 错误。

- `evidence/simd-summary.json`：完整 95% CI、平均阶段耗时、门槛与输入 corpus 元数据。
- `evidence/simd-*-2026-09-06T15-46-01-056Z.json` 与 `.json.raw.gz`：分项摘要和逐 run/逐任务原始数据。
- `evidence/simd-browser-bundle.tar.gz`：实际测量的冻结浏览器 bundle；摘要保存其中每个文件的 SHA-256。
- `evidence/simd-build-manifest.json`：Rust 版本、flags、全部 core/adapter/linker 源码与二进制哈希。
- `evidence/machine.json`、`headless-formal.log.gz`：环境和正式执行记录。
- `evidence/smoke-attempts.json.gz`、`superseded-layout-run.json.gz`：开发短跑/失败与旧布局数据，全部排除出采用结论。

吞吐辅助项 `latencyDerivedTasksPerSecond` 是测量时间的倒数，排除了计时外 hash 校验与 harness 开销，不能当作完整 harness 墙钟吞吐。模块初始化是每场景一次的本机记录；不作为跨机器冷启动分布。当前构建字节数为标量 **1,794 B**、SIMD **3,524 B**，SIMD 增加 **1,730 B**；两者线性内存容量相同。
