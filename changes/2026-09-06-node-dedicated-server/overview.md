## 第一阶段迁什么

迁移完整服务端职责：权威循环、生成与安全出生点、流体和算法 NPC 调度、世界数据驻留、保存与恢复。浏览器继续负责输入、预测、碰撞镜像、mesh 和渲染。

现有 Headless CLI 只证明无 DOM 规则能运行，它使用内存存档和手动推进；现有浏览器主线程还协调计算。因此不能只在 Node 启动一个 `GameServer` 或给 Worker 接 WebSocket 就算迁移完成。

首版按当前代码边界设计为**单世界、单玩家连接**。无人连接、打开菜单和浏览器隐藏都不暂停 Node 世界；断连会清除输入。多玩家、LLM AgentServer 和动态模拟岛是后继合同，不混进本次常驻底座。

Node 使用可部署的 ESM 产物、单写者文件检查点和版本化 WebSocket 协议。关键限制是：客户端能发玩家动作，不能上传权威生成数据、伪造权限或远程关闭世界；重连做完整基线同步，未知结果的动作不自动重试；保存成功必须绑定落盘检查点。

## 第二阶段玩家如何使用

启动页有两个选项：

| 本地世界（此浏览器）             | 连接服务器                         |
| -------------------------------- | ---------------------------------- |
| 沿用 seed、继续/新建与浏览器存档 | 填服务器地址、访问口令并连接       |
| 仍可暂停和保存退出               | 菜单停止输入，服务器继续运行       |
| 默认模式                         | 本机 Node 也在这里填 loopback 地址 |

界面明确显示连接、验证、同步、失败和重连状态，记住非秘密地址配置。两边存档相互独立；连接失败不自动启动一个同 seed 的本地世界。远端 seed/线程参数不由玩家 GUI 修改。

## 第三阶段怎样证明收益

先把迁移所需接线变化用浏览器 B0/B1 对照单独测量，再固定 TS、布局、逻辑工作量和并发角色，比较无网络的浏览器服务端宿主与 Node。之后逐层加入编解码、WebSocket、loopback/LAN 和磁盘存储，得到实际产品净收益。

| 单项实验      | 要回答的问题                                            |
| ------------- | ------------------------------------------------------- |
| TS 线程池扩展 | 固定算法增加工作槽位后，吞吐是否覆盖调度/内存成本？     |
| 真实多进程池  | 相同槽位下，独立 PID 的隔离与执行收益能否覆盖 IPC/RSS？ |
| 共享缓冲区    | 是否真的节约传输成本，还是增加同步与维护负担？          |
| Node I/O 并发 | 不削弱落盘语义的前提下，恢复与保存是否改善？            |

Web Worker 已经能并行，线程池本身不能宣传为 Node 独有收益。多进程只接收候选计算任务，所有修改仍回到单一 Authority 校验提交，不把一个世界随意切成多个并发写者。

每项固定其余变量，报告核心/边界/排队时间、p50/p95/p99、有效吞吐、两端 CPU/内存、GC、启动、网络和持久化成本。最后直接比较全部关闭、单项开启、兼容的正收益集合与消融结果，不相加提升百分比。允许最终保持部分或全部优化关闭。

## 与后续工作的接缝

Wasm 线持有纯 Rust core 和浏览器产物；本线持有 Node 平台、网络、磁盘与 GUI。共享内核采用有界数值批量任务，wire protocol、kernel ABI 和存档容器各自版本化。合并后重新冻结 TS 控制数据；不把布局/语言变化计入 Node 收益。

Node 迁移完成后，Agent 线才以现有 Query/Command/Action 和回执形成玩家交流到可见行为的完整闭环。模型推理异步运行，世界不等待模型响应。

本方案的重点审核项是：首版单玩家范围、远端世界不暂停及断连行为、磁盘检查点的恢复边界、网络允许的能力，以及分层性能归因。所有功能验收仍为待实施；设计审核通过后先写 RED，再按 Node 可玩闭环 → GUI → 分项实验 → 组合验收推进。
