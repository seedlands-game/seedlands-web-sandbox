## 第一阶段迁什么

迁移完整服务端职责：权威循环、生成与安全出生点、流体和算法 NPC 调度、世界数据驻留、保存与恢复。浏览器继续负责输入、预测、碰撞镜像、mesh 和渲染。

原来浏览器协同执行并回送 Authority 的 canonical/Fluid/Logic 计算全部上移，新增[性能不退化门禁](performance-guardrails.md)：同时观察排队/计算/提交、有效世界进展和客户端帧时/碰撞等待/可见延迟。退化必须定位修复、同条件复验；不能以“常驻有价值”放行，也不能通过降低负载或退回客户端计算过关。物理网络时间单独按实测 RTT 与可玩 SLO 验收。

现有 Headless CLI 只证明无 DOM 规则能运行，它使用内存存档和手动推进；现有浏览器主线程还协调计算。因此不能只在 Node 启动一个 `GameServer` 或给 Worker 接 WebSocket 就算迁移完成。

首版按当前代码边界设计为**单世界、单玩家连接**。无人连接、打开菜单和浏览器隐藏都不暂停 Node 世界；断连会清除输入。多玩家、LLM AgentServer 和动态模拟岛是后继合同，不混进本次常驻底座。

Node 使用可部署的 ESM 产物、单写者文件检查点和版本化网络协议。关键限制是：客户端能发玩家动作，不能上传权威生成数据、伪造权限或远程关闭世界；重连做完整基线同步，未知结果的动作不自动重试；保存成功必须绑定落盘检查点。

## 网络协议先做选型，不提前定案

2026-09-07 修订：上版 WebSocket + JSON 元数据/二进制块仅保留为参考。先把可靠事务/库存/世界提交与可替换位姿分开，再固定内容和频率比较 JSON/数值块、专用二进制、Protobuf 的完整编解码与应用成本。固定编码后比较单 WSS、分离大块流量、WebTransport HTTP/3/QUIC 的多流与 datagram；WebRTC DataChannel 先审计连接与运维成本。

对照同时看两端 CPU、分配/GC、线上字节、尾延迟、状态新鲜度、浏览器/UDP 可达性和维护成本。正式 wire v1 在 N0–N4 选型后冻结；Node 无网络宿主与存储可独立推进，参考接线可先跑，但不能等 Node features 做完才决定网络。QUIC 若入选保留可见 WSS fallback，认证/版本错误仍拒绝，断线不分叉为本地世界。

## 第二阶段玩家如何使用

启动页有两个选项：

| 本地世界（此浏览器）             | 连接服务器                         |
| -------------------------------- | ---------------------------------- |
| 沿用 seed、继续/新建与浏览器存档 | 填服务器地址、访问口令并连接       |
| 仍可暂停和保存退出               | 菜单停止输入，服务器继续运行       |
| 默认模式                         | 本机 Node 也在这里填 loopback 地址 |

界面明确显示连接、验证、同步、失败和重连状态，记住非秘密地址配置。两边存档相互独立；连接失败不自动启动一个同 seed 的本地世界。远端 seed/线程参数不由玩家 GUI 修改。

## 第三阶段怎样证明收益

先把迁移所需接线变化用浏览器 B0/B1 对照单独测量，再固定 TS、布局、逻辑工作量和并发角色，比较无网络的浏览器服务端宿主与 Node。之后逐层加入选定的编解码/传输、loopback/LAN 和磁盘存储，得到实际产品净收益；保留 T0/C0 参考，单独列出网络选型收益。

| 单项实验      | 要回答的问题                                            |
| ------------- | ------------------------------------------------------- |
| TS 线程池扩展 | 固定算法增加工作槽位后，吞吐是否覆盖调度/内存成本？     |
| 真实多进程池  | 相同槽位下，独立 PID 的隔离与执行收益能否覆盖 IPC/RSS？ |
| 共享缓冲区    | 是否真的节约传输成本，还是增加同步与维护负担？          |
| Node I/O 并发 | 不削弱落盘语义的前提下，恢复与保存是否改善？            |

Web Worker 已经能并行，线程池本身不能宣传为 Node 独有收益。多进程只接收候选计算任务，所有修改仍回到单一 Authority 校验提交，不把一个世界随意切成多个并发写者。

每项固定其余变量，报告核心/边界/排队时间、p50/p95/p99、有效吞吐、两端 CPU/内存、GC、启动、网络和持久化成本。最后直接比较全部关闭、单项开启、兼容的正收益集合与消融结果，不相加提升百分比。允许最终保持部分或全部优化关闭。

## 新增：现有 MC 宿主上的真实远端测试

现场确认目标是 CT105 `mcs`（Debian 12、x86_64 的 LXC），`mc.bieji.fun` 的 AAAA 与其 IPv6 一致，本机可访问 SSH 22。拟新增独立 8443 HTTPS/WSS 服务、账号与存档，现有 MC/MCSManager/ddns-go 保持隔离。

8443 TCP 只覆盖参考/兼容入口。若采用 WebTransport HTTP/3，还需独立验证同数字 UDP 端口、TLS 与服务端组件；SSH 可达不证明 UDP 可达。选型的 WAN 探针可以先做，正式远端交付等待 N4，并覆盖选定传输和 fallback。

CI 在 main 检查与 Pages 部署成功后，从同次运行取完整 Linux 产物，用 SSH/SFTP 推送并启动，服务器不需要连接 GitHub。独立部署 workflow 避免正在切换时被新 push 取消；有检查点备份、版本校验、外部 smoke 和失败回滚。实际 runner 的 IPv6/SSH 路径尚未验证，不预设 GitHub 能直达；必要时另选已验证的双栈跳板或部署执行点。

真实公网组验证 RTT/jitter、客户端预测校正、断连重连、更新重启和未知动作回执。网络波动注入只在隔离测试流中进行，不改 MC 共用网卡或 DDNS；公网数据与受控 runtime A/B 分开。Node/GUI 本地闭环完成后即可推进，不需要等所有优化实验结束。

## 与后续工作的接缝

Wasm 线持有纯 Rust core 和浏览器产物；本线持有 Node 平台、网络、磁盘与 GUI。共享内核采用有界数值批量任务，wire protocol、kernel ABI 和存档容器各自版本化。合并后重新冻结 TS 控制数据；不把布局/语言变化计入 Node 收益。

Node 迁移完成后，Agent 线才以现有 Query/Command/Action 和回执形成玩家交流到可见行为的完整闭环。模型推理异步运行，世界不等待模型响应。

本方案的重点审核项是：首版单玩家范围、远端世界不暂停及断连行为、磁盘检查点的恢复边界、消息交付语义与网络选型门禁，以及分层性能归因。所有功能验收仍为待实施；设计审核通过后先写 RED，网络前置选型与 Node 基础迁移独立推进，再完成正式 GUI/远端 → Node 分项实验 → 组合验收。
