# Node 迁移实验与收益归因

本文是 [spec](spec.md) 的审核附件。**当前仅定义实验，尚无 Node 性能数据。** 目标允许得出「Node 的价值是常驻与可运维，特定负载并未变快」；功能成立和性能更优分别验收。

用户追加的不退化要求优先于本附件原有的容差/停止建议：[A13 计算上移门禁](performance-guardrails.md)要求完整上移、贯通观测和退化修复。没有额外加速可以成立，已确认核心退化不能仅以常驻价值解释后准出。F1–F4 可保持关闭，迁移本身的 A13 仍必须满足。

2026-09-07 补充：[网络选型 N0–N4](network-selection.md)在正式 wire 冻结前完成，独立比较消息投影/频率、codec/压缩与 transport。本表中的 WS 是 T0 参考路径，不是已采用结论。N4 后以选定网络配置复跑 L2/产品与组合组，并保留 T0/C0 对照；L3/F1–F4 固定同一网络配置，不能将换协议收益计为线程池收益。

## 一、需要分别回答的问题

| 用户关心的问题               | 必须控制的变量                                                      | 不能采用的简化说法                                |
| ---------------------------- | ------------------------------------------------------------------- | ------------------------------------------------- |
| 仅迁移 runtime 有多少收益    | 同一 TS、算法、布局、语料、提交顺序、并发拓扑、逻辑工作量、内存存储 | 浏览器旧架构与 Node 新架构的 FPS 差全部算 runtime |
| 网络付出多少成本             | 同一 Node 执行拓扑，增加 codec/WS/链路；拆 loopback 与 LAN          | 跨机服务器换了 CPU 后，全部差异归功于 Node        |
| 每项 Node feature 有多少增量 | 相同 Node 基线，每次只变一个配置                                    | N0 单线程对「线程池+新算法」称线程收益            |
| 所有有效项一起开后的收益     | 固定最终兼容配置，直接与基线配对，逐项消融                          | 把单项提升百分比相加                              |
| 玩家实际感受到什么           | 相同浏览器、画质、视口、路径、服务器工作量；计入两端资源            | 只展示服务端 kernel 微基准                        |

Node 与 Chromium 的 V8 版本可能不同，无法完全消除引擎实现差异；报告称「这两个已记录宿主版本的执行差异」，不称只改变了一个抽象 runtime 标签。集成模式使用 IndexedDB、Node 使用文件存储的产品比较，也不能被称为纯 runtime。

## 二、基线和控制组

### 2.1 基线登记

- **B0**：本设计同步后的 main 基点 `c777ba8`（文件树与原 `1e3619d` 一致） 的可玩浏览器 Integrated TS。冻结 source/tree、lock、浏览器、环境、画质、视口与当前线程角色；历史成绩不代替本轮重新采样。
- **B1**：完成迁移所需接口/职责拆分后的浏览器 Integrated TS；Wasm 全关。与 Node 共用权威/任务合同和 canonical-only 路径，客户端 mesh 负载独立记录。
- **N-inline**：相同 TS authority 与候选任务在一个 Node JS 执行上下文运行的正确性/单线程参照，异步 I/O 不伪称 JS 并发计算。它不是替代现有五 Worker 浏览器的公平性能基线。
- **N-eq**：Node 等价职责基线：Authority、Logic、Fluid、general、persistence 各一条常驻 lane。其 Worker 适配只是对应已有浏览器并行能力，扩池等 Node 优化全关。
- **N-final**：N-eq 加上经验证正收益且相互兼容的配置集合。互斥的线程/进程执行模式必须选择一种，不能说「所有开关同时开」。

B0 的通用 Worker 同时服务生成与 mesh，B1 可能因为职责拆分改变队列和消息次数。必须先报告 B0/B1 的结构调整成本，记录真实 Worker 图和每个角色工作量；既不隐藏新增 mesh 资源，也不为了凑相同线程总数改变服务端工作。如果 B0→B1 已退化，先定位，不能让 Node 的改进掩盖本地模式退步。

### 2.2 分层矩阵

| 层             | 对照                                                   | 固定项与意义                                                                                     |
| -------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| L0 接缝检查    | B0 / B1；N-inline / N-eq 结果一致性                    | 前者为产品结构成本，后者为 TS 并发路径正确性；都不是 Node 独有收益                               |
| L1 宿主计算    | B1-server-harness / N-eq-server-harness                | 无 renderer、无 WS；相同任务 trace、并发角色、内存 store、逻辑时钟；比较服务端工作与宿主消息成本 |
| L1s 单线程参照 | Browser 单 Worker / N-inline                           | 相同 batch trace、算法、布局和无网络内存 store；辅助判断平台执行差异，不能顶替 L1 或可玩基线     |
| L2a 编解码     | 同一 Node 进程中的已解码输入 / encode-decode loop      | 同样输出被消费与校验；边界 CPU、分配和字节成本，包含消息封套                                     |
| L2b socket     | N-eq 进程 + 同机驱动，内存传输 / WS loopback           | 同一外部驱动、同样逻辑 trace 与响应消费，标清额外 IPC 基准传输成本；不给无法隔离的开销起精确名称 |
| L2c 产品环境   | B1 可玩 / N-eq WS loopback 可玩                        | 真实产品迁移净结果：网络、角色分离、磁盘/IndexedDB、渲染竞争均包含                               |
| L3 分项        | N-eq / N-eq+Fi                                         | 一次一项；同 Node、线程预算、语料与存储策略（除该项本身）                                        |
| L4 组合        | N-eq / N-final；B0 / N-final；B1 / N-final             | Node 优化总收益、相对原版总体收益、相对结构调整后的迁移收益，分别给出                            |
| L5 部署        | N-eq / N-final 在同一 LAN 服务器上，浏览器仍同一客户端 | 固定服务器硬件做分项比较；与 loopback 分开。两台设备的总资源也要计算                             |

L1 的 server-harness 使用生产宿主/任务执行与提交路径，不另写一个简化 GameServer。输入按逻辑 tick 预录；纯 kernel 对照强等价，trace replay 对 async 结果采用预登记逻辑释放点以固定提交顺序，并计入等待。真实时钟可玩组保留生产完成时序，另报 deadline miss、stale/rejected work 和世界进展；更快而少做了工作不是性能优化。

人工延迟 0/50/150 ms 必须标注是**单向**延迟，另测实际 RTT 与 jitter。应用消息故障可沿生产 adapter 的受控 Harness 边界注入，用于状态机正确性；TCP/QUIC 的丢包、拥塞、重传性能必须在隔离网络路径注入并实测，不能用应用 sleep 模拟。网络附件使用的是 RTT 档位，记录时禁止混用。高延迟组用于体验与正确性，不能掺进纯宿主平均值。无权或无法验证真实 LAN 时 A8 保持未完成，loopback 与模拟延迟不冒充 LAN。

## 三、Node feature 逐项实验

所有项目默认关闭或固定基线值，先有正确性和一个代表场景探针，再进入正式矩阵。F1、F2 为用户明确要求的必做实验；F3、F4 至少有有界探针与成本证据，无收益即可停止并记录。Node 独有部署能力与浏览器也能实现的机制分别标明。

| 项目                          | 具体实现与一变量对照                                                                                                       | 主要候选负载                                                                  | 拒绝/停止条件                                                                              |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| F1 TS `worker_threads` 池扩展 | N-eq general=1 对 2、4，再到有用 CPU 预算；常驻池、同 batch 大小和算法；Logic/Fluid lane 先保持 1                          | canonical 生成、安全出生点预计算、有界独立任务                                | 资源争用抵消吞吐或 p95/队列退化；不把建池本身算 Node 独有能力                              |
| F2 真多进程计算池             | general 线程模式对 `child_process.fork` 常驻计算进程；相同工作槽位数、同任务、显式 advanced IPC/数值编码；Authority 不搬家 | 大批生成/流体候选离线语料、持续混合负载；先单 general，再单独试 Fluid backend | IPC/RSS 抵消收益；绝不通过把一个世界复制多份来刷吞吐                                       |
| F3 有界共享缓冲区             | 同 worker 数，专属 ArrayBuffer transfer 对 SharedArrayBuffer slab + 所有权序号；单项只改变传输                             | 大 Chunk/流体 observation，高频复制占比确实高的样本                           | 额外同步复杂度大、尾延迟无益或产生数据竞争；浏览器也可共享内存，但本轮不改变其跨源隔离要求 |
| F4 Node I/O 并发预算          | 相同冻结/codec/fsync 语义，文件读写并发 1 对 2/4；再独立比较默认 libuv pool 对固定更大值                                   | 恢复批量 Chunk、保存期间 streaming                                            | 耐久语义变化、存储设备饱和或 checkpoint p95 退化；不得减少 fsync 换取好看数字              |

F2 的每次 run 记录 supervisor、Authority 所在进程、每个计算子进程 PID、启动时间和任务完成数，要求存在不同存活 PID 且实际执行任务。注入 kill 一个计算进程：工作租约失效、最多一次重新排队、旧 generation 结果丢弃，Authority 仍是唯一写者；重试失败返回明确错误，最多 3 次/分钟进程恢复，越界健康降级。IPC `send()` 积压遵守队列字节上限，不能无限排队。恢复/隔离的收益单独报告，不能用「崩了也不影响进程」推导必然加速。

F1/F2 只并行只读输入的候选计算。流体相邻读写集、Logic 观察版本、Chunk 生成替换都需既有校验；不为增加线程数跳过 read-set 或把 fluid lane 直接无序并发。同一核无内部隐藏线程池，以免超售。F2 第一轮只替换 general executor；需要替换 Fluid 时重新做单项对照，不悄悄把两个角色一起改变。

F3 的 slab 只能传派生快照/结果，绝不共享可写 canonical Store。槽状态 `free → owned → ready → consumed → free` 携带 slot generation、长度与 epoch；旧消费者不得释放新槽；超时回收须确认任务不再访问。不能在 Authority/网络主循环上用阻塞等待。Node worker 的内存限制不等于整个进程 RSS 上限，也不是不可信插件安全沙箱。

F4 中异步文件 I/O 的线程池与运行 TS 的 Worker 是不同资源，`UV_THREADPOOL_SIZE` 不会使 TS 游戏循环自动并行。Node I/O/性能 API 用官方说明核验；只使用冻结 Node 版本可用指标。[文件系统](https://nodejs.org/docs/latest-v22.x/api/fs.html)、[性能观测](https://nodejs.org/api/perf_hooks.html)

当前不进入正式矩阵：`cluster` 多 socket 接入、世界/区域分片、动态模拟岛、全世界常驻、高频物理拆线程、CPU affinity/操作系统调度调优、原生 codec 替换、压缩算法替换。前两类需要多玩家/多权威合同；后几类同时改变语义、算法或跨平台运维成本。Rust Wasm/NAPI/native 是后继语言轴，本轮保持 `kernelBackend=ts`。

上段排除范围针对 F1–F4 的 Node 计算特性矩阵。网络编码/无损压缩的有界对照属于当前 N2 选型，不是推迟到后继；WebTransport 的原生传输适配若必要，作为网络平台成本评估，不改变 TS 游戏内核。

## 四、负载与可比性

| 场景     | 固定内容                                                             | 主要指标                                                            |
| -------- | -------------------------------------------------------------------- | ------------------------------------------------------------------- |
| W-start  | 固定 seed、版本、出生点搜索范围；新世界/已有存档分开                 | 启动到可连接、首场景可玩、生成吞吐与冷内存                          |
| W-stream | 固定路线、Chunk 请求 trace、视距与镜头，含跨 Chunk 移动              | 就绪 Chunk/s、queue wait p95、碰撞等待、frame p95                   |
| W-fluid  | 固定跨 Chunk 流体输入、初始边界和候选批量                            | 有效 candidate/s、计算/复制/提交时长、过期率                        |
| W-actors | 相同实体状态、随机种子、导航/感知预算；32/128/512 档中符合当前上限者 | gameplay/logic tick p95、有效 action/s、deadline miss               |
| W-save   | 冻结 corpus 的小/中/大存档，按 dirty 比例和总索引大小分桶            | checkpoint p95、durable 延迟、读取/编码/fsync/RSS                   |
| W-mixed  | 同时移动、编辑、NPC、流体和周期保存；固定动作速率                    | 主要产品指标：输入到权威确认 p95；服务端 deadline miss 与 frame p95 |
| W-idle   | 无连接仍运行的固定活跃窗口，另有连接但无输入                         | tick 连续性、NPC 进展、CPU/RSS 增长、保存跨度                       |

不得提高当前 512 retained actor 上限或修改 AI/流体预算来构造 Node 胜利；若当前上限只能容纳更小活跃集，按真实配置冻结并报告。不同场景可选择实际有效的热点规模，不要求把 512 个实体都强制进入全精度以扩大本合同。

每个 corpus 登记 seed、generatorVersion、physics/fluid/gameplay schema、Chunk/实体/动作数、输入 bytes、snapshot hash、trace hash 和预期输出摘要。生成/codec/流体纯数值核要求逐项等价；浮点轨迹如需容差，先按现有物理测试定义容差与误差指标并绑定合同，不采样后再放宽。checksum 相等只是快速过滤，至少保留可定位字段/Chunk 的完整校验路径。

## 五、采样协议和指标

### 正式样本

1. 先冻结配置、主要指标、负载和失败判据。A/A 至少 5 对估计环境噪声与埋点开销；噪声超过拟议最小收益则改善环境或判无法区分。
2. 每场景/候选至少 10 个独立配对 run，交替或随机 AB/BA，记录顺序；固定 warm-up 30 秒、steady-state 120 秒。一次运行内的数千 tick 不是数千独立样本。
3. 冷启动单独 10 次新进程/新浏览器 context；缓存冷/热明示，文件系统 page cache 无法重置就报告 warm-cache，不能靠重启应用宣称冷盘。
4. 吞吐组完成同样的 N 项有效任务；实时组固定时长和相同 offered load，记录 completed/backlog/rejected，吞吐与完成工作量一起展示。
5. 每次使用新隔离世界/临时数据目录；每个失败、fallback、OOM、timeout、crash 保留并报告，不静默删除。故障实验不混入常态性能样本，但发生非注入故障的配置不能凭余下成功样本被采用。
6. 浏览器性能运行时不截图、不 Midscene、不 readback；可见旅程另行验收。其他 agent/构建/实验不能争用采样设备。环境热节流、前后台状态、供电与 CPU 配置写入 run metadata。
7. macOS 与 Linux、headless 与 headed、loopback 与 LAN 分组展示。自动化可先 headless；人工/真实屏幕观感不以 headless FPS 替代。完整组合补一次 30 分钟稳定性运行，观测内存趋势、队列与检查点。

Node 记录每 lane 的 enqueue/start/end/receive/validate/commit 本地单调时间。跨进程和跨机器时间原点不能直接相减：CPU 阶段在所属进程计时，端到端由发送方 request id 的往返计时；跨机一方向延迟无可靠时钟校准则 `NOT_COLLECTED`。

| 指标组    | 最少内容                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------- |
| 计算/调度 | 核心时间、排队、候选校验与提交；tick p50/p95/p99、deadline miss、backlog、有效任务/s                       |
| 边界/网络 | 编码/解码、copy/transfer/slab 成本、payload 与实际 frame bytes、消息/s、RTT p50/p95/p99、重同步率          |
| 资源      | 每进程 RSS、同进程各 Worker heap、external/ArrayBuffer、CPU、GC、event loop delay/utilization、进程/线程数 |
| 产品      | 输入到权威确认、显示反馈延迟、prediction correction、碰撞等待、首可玩时间、frame p50/p95/p99               |
| 持久化    | 冻结、编码、写入、sync、发布、durable checkpoint 延迟、保存失败与积压                                      |
| 工程成本  | 包体、冷启动、平台依赖、配置与故障恢复复杂度、测试/维护路径、实现和返工成本（未知写 unknown）              |

RSS 以进程计，不能把同一 Node 进程中每个 Worker 的 `process.memoryUsage().rss` 累加；多进程 RSS 之和标明包含共享页重复计数，能取得 PSS 时另报。浏览器相关进程与 Node 总资源一起给出，避免只看浏览器降内存。浏览器缺失 GC/RSS/CDP 指标记 `UNSUPPORTED` 或 `NOT_COLLECTED`，不填 0。

## 六、统计与采用规则

每对 run 对主要指标计算相对变化和绝对差；对独立 run 配对 bootstrap 95% CI，展示每次原始值、p50/p95/p99 和异常/失败数，不把所有 tick 混池制造极窄区间。宿主结果以主指标与辅助资源一起解释；frame、server tick、CPU 时间不能合并成单个「性能百分比」。

F1–F4 先预登记一个主要指标和一个目标场景集合；建议采用门槛：该主要指标改善 ≥10%、配对 95% CI 下界 >0，耗时指标绝对改善 ≥1 ms（批任务按整批计），同时全部目标场景 p95 无已确认超过 5% 的退化，正确性与故障门禁通过。吞吐指标用有效工作/s，不要求额外 1 ms；若内存增加 >20%，仅可提出明确的隔离/容量取舍方案，不能默认启用。阈值是项目提案，可在审核前调整，不能看完结果再挑标准。

样本在预算内无法区分噪声则结论为「不确定、默认关闭」，不用不断重跑直到显著。先筛选后用独立 holdout 配对验证入选配置，减少多候选择优偏差；没有预登记的次要指标改善只能作为探索发现。

N-final 与 N-eq 必须直接比较，逐项关闭候选进行消融；组合未过门槛则缩减集合或保持 N-eq。B0/B1/N-final 都报告实际可玩净结果，允许 Node 网络开销导致玩家延迟增大。资源隔离或常驻能力仍可构成产品价值，但不能因此把负收益说成性能提升。

上段的网络延迟增加仅指按实测链路预算解释的传输时间，仍须通过 A13 的预测/碰撞/世界进展与 WAN SLO。旧 5% F1–F4 次指标容差不能豁免 A13：核心退化必须修复，区间不确定保持未完成，不能通过降低频率/负载或把计算退回不可信客户端过关。修复后的最终配置要与 B0/B1 及全关参考直接对比。

## 七、证据格式与预算

本节只计算机器采样量；PD、Agent 工作、工具等待、credits/API/额度与 20% 缓冲统一在[工作量附件](estimates.md)，避免将机器等待当作全部 AI 工时或重复叠加。

输出关联字段至少包括 `runId`、`pairId`、`layer`、`sourceSha`、`sourceTree`、`lockHash`、`artifactHashes`、`corpusHash`、`configHash`、Node/V8/Chromium/OS/CPU、角色拓扑、PID、cache 状态、执行顺序、原始指标文件 hash、正确性与失败记录。每份汇总必须能回到具体原始数据。临时大型数据留忽略目录；提交精简 manifest、结论、必要可复核样本及原始证据归档位置/hash，不提交依赖或构建目录。

采样矩阵采用稀疏阶段：L0/L1 必跑 → L2/W-mixed 网络成本 → F1/F2 代表热点 → F3/F4 探针 → 入选项完整目标场景 → L4 holdout/消融 → L5/稳定性。不同拓扑、核数、场景、语言不得直接做全笛卡尔积。

该顺序是收益归因矩阵，不替代实施门禁：网络 N0–N4 先于正式 wire/GUI 交付及 F1–F4 产品比较。网络探针预算单列，先能力淘汰和代表场景，再对入选项使用正式配对；下列 12–20 格预算不自动涵盖新增网络矩阵。

以每个正式配置/场景 10 对、每 arm 150 秒估算，一格约 50 分钟纯采样；环境/启动另计。先冻结约 12–20 个高价值格子，约 10–17 小时机器采样，再按候选结果决定扩展。这是计算预算示例，不是实现工期或承诺当前设备能无干扰完成；范围扩大要说明新的成本与价值。

最终交付表每行包含：B0/B1 结构成本、宿主收益、网络成本、F1–F4 结论、最终组合收益、macOS/Linux/LAN 适用范围、是否默认开启、维护/资源代价、未采集指标。无收益项也必须留下有效结论；不得只交一张最高 FPS 图。

## 八、真实公网补充层

用户新增 CT105 `mcs` / `mc.bieji.fun` 测试环境，追加 `WAN-direct-v6` 组，目标是实际 RTT/jitter、预测校正、断连回退与更新恢复正确性。部署、故障注入范围、自然网络样本与证据边界按 [远端附件](remote-environment.md)；CI 可达和浏览器公网可达分别验真。MC 共享资源干扰必须记录，不能把公网/跨设备差异归功于 Node runtime。原 L0–L5 和 F1–F4 的受控比较保留，不因具备远端服务器而省略。
