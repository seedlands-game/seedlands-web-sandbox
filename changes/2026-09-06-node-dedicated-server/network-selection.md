# 消息、编解码与网络传输选型

**2026-09-07 修订：WebSocket 与 JSON 元数据/二进制块仅为参考组，尚未选定正式协议。** 上版过早收敛了技术选择，没有通过项目负载和网络实验。这里把选型前移到网络接口冻结之前；不等 Node feature 实验做完后才考虑，也不因参考实现先跑通就默认采用。

本文与 [spec](spec.md)、[实验合同](experiments.md)、[远端附件](remote-environment.md)共同参与审核。本轮只完善方案，不实现协议、安装 QUIC 库或开放 UDP 端口。

## 一、先分开三类决策

1. **消息语义与同步策略**：发什么、给谁、多久发一次、是否允许丢弃、增量依赖哪个基线、如何确认与恢复。
2. **消息的字节表示**：schema、字段类型、打包/编码、压缩、应用层分块；权衡两端 CPU、分配/GC、包体与演进成本。
3. **传输与连接**：有序/可靠流或 datagram、多流隔离、拥塞控制、TLS、浏览器和服务端支持、UDP 可达性及 fallback。

codec 的一条 message、WebSocket frame、TLS record、QUIC frame 和 IP packet 不是一一对应。报告区分应用载荷字节、封装字节、加密/网络实际字节和重传，不能用 `JSON.stringify(...).length` 当带宽。

TCP/UDP 是传输层候选，QUIC 建立在 UDP 上但同时提供可靠流、加密及拥塞控制；HTTP/3 使用 QUIC。普通网页不能像 Node 的 `net`/`dgram` 一样任意创建原始 TCP/UDP socket，实际需要选择可用的浏览器 API。HTTP 请求用于资源和控制，不因升级 HTTP/3 就自动变成可发送任意不可靠游戏消息的接口。[QUIC RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)、[WebTransport API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport)

## 二、先拆当前消息，避免被传输锁住

源码 `src/worker/authority-worker.ts` 的 tick 对 snapshot 发布作约 60 Hz 上限门控、每至少 50 ms 附带 Gameplay，并可混带 commits；实际频率受唤醒/负载影响。`AuthoritySnapshot` 包含实体 Body、contacts、Chunk revision 和 diagnostics，`AuthorityGameplayView` 又有实体/actor 数据。这是浏览器内存消息现状，不是已验证的网络 DTO 或发送预算。

先列消费方和字段，建立公共视图，去除仅诊断/服务端编排需要的数据，并单独记录这一投影的收益。再在同一投影和同一发送频率上比较 codec/transport。不能因 QUIC 组少发了字段，就把省流量归功于 QUIC；也不把模拟 tick Hz 直接当成网络更新 Hz。

| 消息类别                                      | 必须保留的语义                                                     | 候选交付方式                                                                    |
| --------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 握手、身份、配置/版本                         | 可靠、有序、明确状态转换                                           | 可靠控制流                                                                      |
| 放置/破坏事务、制作、库存、动作结果、世界提交 | 可靠交付或明确失败；epoch/sequence 去重，跨断线不声称 exactly-once | 有界可靠控制/事件流，不混入可丢弃 pose 包                                       |
| 持续移动/朝向/按住状态                        | 允许新状态替换旧状态；按服务器 tick 验证、序号、输入租期、确认     | 可靠参考；另测带有界冗余/序号的 datagram                                        |
| 跳跃边沿等一次性输入                          | 不能靠“最新输入覆盖”丢掉；过期也不能晚到重做                       | 显式 edge id + 有界去重/期限/确认，先保留可靠方式，再单独验证 datagram 冗余方案 |
| 实体 pose 展示快照                            | 旧状态可丢，latest 可用不意味着所有字段都可丢                      | 可独立解释的 pose datagram，或相对已确认基线的 delta；缺基线请求完整状态        |
| 初始世界、Chunk/流体基线与版本化增量          | 完整、可校验、可取消、依赖显式                                     | 单独有界可靠流/分块，避开控制消息排队                                           |
| 调试/性能统计                                 | 可降频或禁用，不决定权威状态                                       | 有限低优先级消息，正式性能组控制观测成本                                        |

可靠提交序号、Chunk revision 与 pose 所依赖的最低版本建立因果屏障；即使多条 QUIC stream 都可靠，也没有跨 stream 自动全局排序。Chunk/事件未到时，客户端等待/重同步相关状态，不能先用新 pose 与旧碰撞基线制造穿透。

现在冻结的是这些业务语义、身份/版本和资源上限，不冻结统一的全局 FIFO。传输端口表达消息类别、可靠性、期限与背压/取消，并报告协商后的能力；它不能只提供一个假设永远可靠有序的 `send(any)`。不过不提前实现没人消费的完整通用网络框架。

## 三、传输候选与第一轮取舍

| 候选                                                      | 值得验证的收益                                                              | 成本与边界                                                                                            | 本轮角色                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| T0 单连接 WSS，参考 `ws` 的 HTTP/1.1 Upgrade/TLS/TCP 路径 | 接线和运维简单，便于建立可复现参考                                          | 一个有序字节流；丢包后的重传等待可能让后续新快照也等待；已进入传输栈的旧消息不能靠应用队列合并撤回    | 必做参考，不自动成为最终默认                          |
| T1 WSS 控制与大块数据分离，或大块走独立 HTTP 请求         | 验证是否低成本缓解大 Chunk 对实时控制的排队                                 | 多连接/请求有额外握手与公平性成本；HTTP/2 共用 TCP 时仍可能共享传输层阻塞；记录实际连接映射           | 小型控制组，避免只拿未经调度的最差 WS 对比 QUIC       |
| T2 WebTransport over HTTP/3/QUIC                          | 控制/Chunk 用独立可靠流，pose 等用 datagram；减少跨流重传阻塞、丢弃过期状态 | UDP/HTTP3 服务端实现、证书、客户端版本、MTU/大小与速率限制；多流仍共享拥塞窗口，不是无阻塞/必然低延迟 | 主要比较对象，必须做能力/连通性及代表负载探针         |
| T3 WebRTC DataChannel                                     | 可配置有序/无序和部分可靠性                                                 | SCTP/DTLS、ICE/信令、可能的 STUN/TURN；转发会改变时延和运维成本；本项目当前是浏览器到公开服务器       | 必做架构审计；T2 不能覆盖目标环境时再进入有界性能原型 |
| REST 轮询 / SSE                                           | 资源、诊断和低频管理简单                                                    | 不作为高频双向游戏数据的主要候选；仍有请求/连接与可靠流语义                                           | 静态资源/控制辅助                                     |
| 裸 TCP / UDP、自造可靠 UDP                                | 对普通网页不可直接替换上述 API                                              | 引入本地客户端/浏览器特权容器将改变产品边界                                                           | 本次排除                                              |

WebTransport 的可靠流与不可靠 datagram 能力见 [API 文档](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport)；[W3C 工作草案](https://w3c.github.io/webtransport/)仍需按实际浏览器实现核对。不要沿用“所有浏览器都不支持 WebTransport”的旧印象，也不能把 API 存在当作全部能力可用。WebRTC 的 SCTP/DTLS 和部分可靠性见 [RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html)。

T2 必须登记真实协议：HTTP/3/QUIC 还是可靠-only 的兼容路径、datagram 是否可用。可靠-only fallback 不计入 QUIC/datagram 性能组。大于协商 datagram 大小的数据不能按旧“1 MiB frame”上限直接塞入；先限定小且独立的实时消息，大对象走流，避免自造可靠分片层。

冻结 Node 22 基线不能据此假设存在生产可用的内置 HTTP/3 WebTransport server。探针要明确具体库、版本、原生依赖/sidecar、许可证、Linux x64 离线分发、资源和错误隔离成本。若必须增加原生桥接，仍由 TS 持有游戏权威，不能顺势扩成 Rust world server；适配器与部署合同更新后才纳入产品。

## 四、编解码候选与 CPU/体积权衡

先采集真实消息 corpus：小输入/动作、不同实体数量的 pose/Gameplay、中/大 Chunk 基线及 delta；包含正常与畸形输入。每条登记业务 schema、原字段值、数量、频率和消费者所需状态。

| 候选                              | 第一轮对照范围                                                    | 要付出的成本                                                                      |
| --------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| C0 JSON 元数据 + 明确类型的数值块 | 上版设计作为容易检查的参考                                        | 字符串编码、解析、分配、重复字段名与数值表示；不宣称必然最慢                      |
| C1 schema 专用二进制              | 高频输入/pose 固定字段与批量数值；控制消息仍可独立选型            | 显式边界/对齐/字节序、演进与调试工具；JS DataView 循环不保证比原生 JSON parser 快 |
| C2 Protobuf                       | 同 schema 消息，明确 packed fields/bytes；固定生成代码/运行时版本 | varint、对象重建、生成链路、浏览器体积；小包编码紧凑不保证每种负载 CPU 更低       |
| MessagePack / CBOR                | 若 C0 元数据占比大且 schema 频繁变化，补一个通用二进制探针        | 别把“二进制 JSON”当作天然低分配；没有新信息就不展开完整矩阵                       |
| FlatBuffers                       | 若大消息解码/对象物化已成为热点，补读取路径探针                   | 构造、随机读取和转入现有 Store 的成本；最终仍需复制时不得宣称端到端零拷贝         |

第一轮只正式比较 C0/C1/C2，避免无证据地维护五种 codec。编码机制参考 [Protobuf 官方格式](https://protobuf.dev/programming-guides/encoding/)、[MessagePack](https://msgpack.org/)、[FlatBuffers](https://flatbuffers.dev/)，产品优劣只由本项目样本决定。

**体积策略是另一个实验轴**：字段投影/去重、发送频率、兴趣区域、增量/keyframe、量化、压缩分别登记。首轮 codec 强等价，不把 f64 改 f32/定点或缩小坐标范围夹带为编码优化。量化若有价值，需要先给出范围、误差预算和预测/碰撞验收，并修改合同；不允许同 seed 世界数据变化。增量依赖可恢复的明确基线，统计基线重传与状态恢复成本。

大 Chunk 才测无压缩与一种已可离线部署的无损压缩（先 gzip 作为参考）；先测既有 Chunk codec，避免重复压缩。小输入默认无压缩参考，是否保留压缩由总成本决定。codec、压缩窗口/级别、batch 大小每次只改一项；不在主线程同步做整帧大压缩。压缩后也限制解压大小和 CPU/内存预算。

逐项记录两端：投影/编码/复制/发送排队/解码/校验/应用到镜像或 Store 的时间，p50/p95/p99、每消息及每秒分配、GC、浏览器包体、冷启动；大小按原始业务数据、应用封套、压缩后和线上传输分层记录。低带宽下省字节能降低排队，但低 RTT/LAN 下 codec CPU 可能占主导。仅作解释可用 `CPU与排队成本 + 传输字节/有效吞吐`，实际成本会重叠，最终以输入到权威确认/显示与状态新鲜度实测为准。

## 五、实验顺序：先对照，再冻结协议

| 门禁            | 做什么                                                                                  | 交付与停止条件                                                                                        |
| --------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| N0 语义与现状   | 公共消息投影、消费者、可靠性/期限、当前频率/大小直方图                                  | 明确哪些消息可丢；禁止照抄 Worker snapshot 上网                                                       |
| N1 能力探针     | T0/T2 真实浏览器到服务器的可靠流、datagram、TLS、UDP 可达性；T1 小控制；T3 架构成本审计 | 固定目标浏览器及最低版本，含 Chromium/Firefox/WebKit 桌面与拟支持移动端；不能以历史兼容表代替实际验证 |
| N2 编解码       | 同 corpus、同投影、同频率、同 T0，比较 C0/C1/C2；Node encode/browser decode 与反向分开  | 强等价、畸形输入、完整应用成本与体积曲线；无法区分则保留更简单候选                                    |
| N3 传输         | 固定入选 codec/频率/资源，T0/T1/T2；T2 先全可靠多流，再只把允许丢的消息改 datagram      | 区分多流、datagram 和字段/codec 收益；必要时 T3 有界原型                                              |
| N4 合并网络方案 | 最佳可维护 codec + 消息/流分配 + fallback；回到真实可玩/WAN验证                         | 网络默认与支持范围有证据；然后冻结 wire v1 和正式 GUI/部署入口                                        |

采样复用原实验合同的独立配对、A/A、holdout、run/source/config/corpus hash。网络条件预登记 RTT 0/50/150/300 ms、代表性 jitter、带宽限制、0/1/3% 丢包和短时 burst loss，但先做稀疏代表场景，避免全排列；这里是 **RTT**，不能混用旧实验中的单向延迟值。通过隔离网络路径设置并实测验证实际条件；正式性能不用 JS sleep 假装 TCP/QUIC 丢包。

重点场景是大 Chunk streaming 与实时输入同时发生、带宽受限和丢包时的尾延迟/最新有效状态年龄。记录连接成功率、可达性、fallback 次数与耗时、重传、有效 goodput、correction 幅度/频率、错误动作数、两端 CPU/内存。对 transport 不能只比平均 ping；对 codec 不能只比最小 packet。

正确性、权限/重放边界和目标平台覆盖先过门槛；复杂候选默认采用至少需要在预登记目标场景将输入确认 p95 或状态年龄 p95 改善 ≥10%，配对 95% CI 下界 >0，且无已确认超过 5% 的其他核心尾延迟退化。明确网络字节瓶颈时可预登记带宽为主指标；不能看完结果后换主指标。资源增加 >20%、新增 native/sidecar、目标浏览器支持降级等须给具体代价与取舍，不能仅凭快一个场景自动采用。无显著收益则保留 WSS 或混合方案，并留下已完成的对照结论。

2026-09-07 用户追加[A13 计算上移不退化](performance-guardrails.md)后，上段的 5% 候选容差不再适用于 A13 核心指标；任何已确认的核心退化必须修复。网络选型必须连同生成/Fluid/Logic 上移后有效工作与客户端镜像/显示一起验收，不只验证 codec 微基准。修复与新增采样计入[双口径预算](estimates.md)，不能用缩减工作量刷收益。

## 六、兼容与部署影响

- 如果采用 T2，保留 WSS 兼容入口；有界能力探测/连接失败后允许降级到 WSS，UI 可观察。认证错误、世界版本不匹配不能通过换 transport 绕过。正在运行时切换以新连接代次 resync，关闭旧写通道，避免两条链路重复执行动作。
- fallback 是网络传输降级，不是另开本地世界。强制 T2 的 benchmark 中发生 fallback 标明该 run 不属于 T2，不能隐藏失败后拿 WSS 数据归功于 QUIC；可用性组则统计完整失败/恢复成本。
- CT105 的 8443 仅是候选数字端口：WSS 使用 TCP，WebTransport HTTP/3 另需 UDP。两者可用相同数字，但属于两条独立监听/防火墙规则，已有 TCP/SSH 可达并不证明 UDP 可达。当前未开放任何新端口。
- Node HTTPS + `ws` 入口只覆盖 T0/T1 参考，不能承诺直接服务 HTTP/3；若 T2 入选，完整离线产物、TLS 接入、CI smoke 和故障恢复都纳入对应组件。GitHub 的 SSH 部署通道与游戏数据通道互相独立。

## 七、准出、边界与当前状态

当前为设计修订，N0–N4 均未跑，无 packet/transport 采用结论。Node 无网络宿主、权威规则和持久化设计可以推进；网络可先使用明确标注的 T0/C0 参考验证接线，但**正式网络接口冻结、GUI/远端交付与最终迁移收益结论必须等待 N4**。不会把待完成的对照实验换成“以后再优化”。

拟定用例：`tests/server/network-message-semantics.test.ts`（可靠/可丢消息分离、delta基线、跨流因果）、`tests/server/network-codecs.test.ts`（强等价/版本/畸形长度/解压预算）、`tests/client/transport-fallback.test.ts`（权限不绕过、旧连接/重复动作）、当前 change 的 `e2e/network-transports.spec.ts` 与 `e2e/network-codecs-benchmark.spec.ts`（真实浏览器与有界网络条件）。先 RED 再实现；独立可丢弃能力原型只在 `/tmp`，不进入生产路径。

准出证据：消息/codec 正确性为 Vitest；能力/交互/fallback 为 Playwright-change；可见降级/恢复反馈为 Midscene；依赖、schema 版本与产物为 Static/Build；真实 UDP/IPv6/平台设备为 Manual supplement 加真实浏览器证据。分别记录未支持/未采集/不确定，不能以 T0 通过代替 T2 已验证。
