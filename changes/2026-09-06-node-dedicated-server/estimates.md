# 工作量、AI 成本与连续运行预算

版本：2026-09-07；范围：从本设计通过审核起到 A1–A14 的 Node/网络/GUI/远端/性能准出，包含必要性能修复。此前方案编写是已发生成本，尚无完整 usage，记 unknown，不计入下面的剩余实施预算。遵守[工作区估算规范](../../docs/change-estimation.md)，并参与本 change 的精确 hash 审核。

**置信度：偏低的规划估算，没有本项目同类全流程的计费/工时标定。** 数字用于比较规模和设预算，不是报价、实测吞吐或保证完成的上界。传统量和 AI 时间独立拆分，不按固定加速倍数换算。协议实现/跨平台支持、性能退化修复与 CI IPv6 是主要不确定性。

## 一、分阶段工作量

1 PD=8 小时熟悉项目的工程师有效工作，包含设计、实现、联调、测试和通常返工。AI 列为单个活动 agent、工具可无人值守、一天 24 小时可用的情景；没有假定本轮获授权启动并行 agent。正常估计取各工时范围中点，保守取右端；下表不含额外 20% buffer。

| 工作包                                           | 传统 PD      | Agent 活跃小时 | 不重叠机器/工具小时 | 正常工作单元 |
| ------------------------------------------------ | ------------ | -------------- | ------------------- | ------------ |
| 职责清单、公共消息投影、迁移基线及观测链路       | 3–5          | 4–6            | 1–2                 | 5            |
| N0–N4 codec/网络选型、跨流语义与能力/网络探针    | 8–13         | 12–20          | 6–10                | 14           |
| Node 宿主、生成/Fluid/Logic 上移、队列与生命周期 | 7–10         | 10–16          | 2–4                 | 12           |
| 冻结存储、故障注入、独占锁与恢复                 | 5–8          | 8–12           | 2–3                 | 9            |
| 双模式 GUI、预测/重连/降级与语义验收             | 5–8          | 8–14           | 2–4                 | 9            |
| CT105、离线包、TLS/SSH CI、回滚与 WAN            | 3–5          | 5–8            | 2–4                 | 6            |
| F1–F4 与计算上移退化定位/修复/复验               | 7–11         | 10–16          | 8–13                | 12           |
| 最终组合、holdout、回归、文档与交付              | 5–8          | 9–16           | 2–5                 | 8            |
| 合计                                             | **43–68 PD** | **66–108 h**   | **25–45 h**         | **75**       |

传统正常量约 55.5 PD；不代表需要 55.5 个自然日，也不含工程师现金报价。AI 无并发墙钟为 91–153 h，正常约 122 h，即 **3.8–6.4 个连续日，正常约 5.1 日**；保守 153 h ×1.2 向上取整为 **184 h，约 7.7 个连续日**。机器时间包含网络、runtime/feature 正式采样与 CI/soak，不再把实验附件的 10–17 h 重复相加。若将独立机器等待与实现重叠，可缩短关键路径，但先画出依赖/资源，不能直接相减所有等待。

以上包含通常一次定位修复与必要复验；若高风险网络适配需要另建 native 服务、系统性重做预测或多轮大修，先更新剩余估算。人工审核、账户限流/reset、缺证书/网络入口等外部等待单列为 unknown，实际交付时间 = 上述连续路径 + 外部等待。24h 口径不是保证可绕过额度连续生成。

## 二、正常任务与消费假设

一个工作单元是一段有明确产物和验证的子任务，可跨多次模型调用，包含阅读、实现/分析、通常返工、校验和上下文恢复；不是一次用户消息。先按每单元 **未缓存输入 80k、缓存输入 240k、计费输出 20k** 做规划，输出含 reasoning；这是待校准假设，不能由任务时长反推为实测速率。单次请求控制在费率的长上下文阈值以内，单元总量跨请求累加。实际每次 usage 按模型登记，避免缓存重复计数。

规模情景为 50 / 75 / 110 单元，75 来自上表，50 表示较少返工，110 表示更多集成/复验。正常缓存输入比例 75%；另列无缓存情景，防止 20% buffer 掩盖缓存命中率风险。高 effort、反复大上下文、视觉评审等可能改变 O/U/C，首个代表阶段必须用真实数据重估。

这张表只比较相同 token 数的单价敏感性，**不宣称更便宜模型能用相同任务数/时间完成本 change**。成本主口径保守沿用当前 Astra；未来按既有路由混用模型时逐项加总实际 U/C/O 与返工，重新估计墙钟。本页不把模型路由建议变成启动子 agent 的指令。

credits 与 API 的 Fast 倍率分别查证：本次官方列 Astra credits Fast 为 2.5 倍，API Fast 为 2 倍，不能共用。API cache-write 另有 1.25 倍输入费率，长上下文也有额外倍率；下表将 cache-write 风险显式纳入保守美元值，不默认享受 Batch/Flex 折扣。Sol 促销有时效，后续 goal 必须重查费率。

## 四、费用情景与 20% 预算

| 情景                         | 未缓存/缓存/输出 MTok                       | Astra credits           | API 等价 USD（基础文本） |
| ---------------------------- | ------------------------------------------- | ----------------------- | ------------------------ |
| 较少返工：50 单元，75% 缓存  | 4 / 12 / 1                                  | 2550                    | 102.00                   |
| 正常：75 单元，75% 缓存      | 6 / 18 / 1.5                                | **3825**                | **153.00**               |
| 更多返工：110 单元，75% 缓存 | 8.8 / 26.4 / 2.2                            | 5610                    | 224.40                   |
| 保守：110 单元，无缓存命中   | 35.2 / 0 / 2.2                              | **11550**               | 462.00                   |
| API 额外 cache-write 敏感性  | 同保守量，所有输入按 12.5 USD/MTok 上界估价 | 不捏造 credits 未列费项 | **550.00**               |

正常 `credits = 6×250 + 18×25 + 1.5×1250 = 3825`；美元独立计算 `6×10 + 18×1 + 1.5×50 = 153`。两列是两种结算情景，不是同时花费的两个账单；本账户订阅内本任务增量现金支出尚无法据此确认。

建议未来整体 goal 的管理预算选保守剩余值再加一次 20%：**13,860 credits；若走 API，文本费用上限建议 USD 660.00；连续墙钟 184 h**。美元选择 550 而非 462 作为基数，是显式覆盖 cache-write 敏感性；credits 按已公布的独立 rate card 算。Fast/超过长上下文阈值不在该 Standard 建议中，采用时重估，不能静默吃掉缓冲。

托管 CI 超额分钟、付费搜索/视觉模型、证书/网络新设施、税费与 credits 实际采购折扣目前缺账户单价，分别记 unknown；已有 MC 硬件不在本次重新采购。USD 660 是**文本 API 子预算**，不是包含所有工具的全包美元硬帽。创建完整付费 goal 前需填写这些费项或明确限定可用免费/现有资源；不自动开支。开发过程的模型成本与后继游戏内 LLM Agent 推理成本分开，后者不在本 change。

为降低一次性大预算的不确定性，建议先以最多 8 单元完成可恢复的职责/计量校准阶段，再决定剩余范围。按同一保守假设，其建议子预算为 `8×105×1.2 = 1008 credits`，API 为 `8×5×1.2 = USD 48`；它属于整体预算内部，不能额外叠加。此处只是预算建议，不创建 goal。

## 五、当前额度与可承受性

本轮额度接口快照时间约为 2026-09-07 00:10（Asia/Shanghai）：主 `codex` 7 日窗口已用 **22%**、剩余 **78%**，reset 为 **2026-09-13 22:50:05 +08:00**；附加消费 credits 余额 **0**。接口同时有 Spark 独立窗口，不能把其剩余比例合并到 Astra。没有消费 reset 或购买 credits；不保存账号 ID、凭据或 reset 凭据。

**本 change 将占当前剩余额度多少：unknown。** 接口没给 included window 的 credits 容量，不能算 `13860 / 78%`，也不能把余额 0 理解为订阅没有可用额度。若取得该窗口总量 Q（且与预测同一口径），则占当前剩余比例为 `预计消耗 / (0.78×Q)`；没有 Q 时保留未知。

校准：在无其他任务、未跨 reset 的代表阶段前后读取窗口，并记录本阶段任务单元/模型/usage。若 k 个单元消耗 d 个百分点，则剩余 n 个相似单元可探索估计 `n×d/k` 个百分点，占当前剩余约 `n×d/(k×78)`；比例由百分比显示的舍入、上下文和其他会话影响，不能称账单。额度占比无法隔离时继续用 unknown，并保留独立 API/credits 预算。审批/reset 等待不得被 24h 口径隐藏。

## 六、goal 与回填

当前 `create_goal` 只有 `token_budget`，不能输入 credits/USD/hour 硬帽。上面的 13,860 是 credits 建议，**不能直接填为 token_budget**。模型 API 累计 input/cache/output token 也不保证等于 goal 的运行计数；正式创建前用可用计量确认口径，再为 token 单独计算 120% 上限，同时保留 credits/美元管理预算。本轮没有创建或更新 goal。
