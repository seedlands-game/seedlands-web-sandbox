# 可组合玩法架构：小内核、标准模块与 Playbook

> 更新：2026-09-09。状态：用户确认的长期架构方向；不是已实现能力清单，也不是已发布的稳定 API v1。
>
> 本文统一“模块、模组、Playbook、Ruleset”及其所有权。具体功能、源码路径和验收由各 change 冻结。[第一期合同](../changes/2026-09-09-composable-overworld-playbook/spec.md)以已合并 #25 的主干为基线，独立交付，不依赖其他活动分支。

## 1. 目的与适用边界

让作者在体素开放世界框架内表达不同玩法：可以直接采用第一方标准机制、通过配置/代码扩展，也可按同一合同创造替代模块。现有 MC 类玩法必须成为普通 API 消费者，而不是核心保留一套特例、第三方只能改变参数。

长期产品仍是 [Promptable Living World](product-positioning.md)。可靠的标准能力提高作品下限，并为未来 AI 创作减少重复工作；不等于本期就实现 AI 生成或完整现代整合包体验。FPS、高难生存、休闲、工业自动化、经营/策略、RPG 等未来参照由用户提供后逐项建立场景和质量预算，不凭“Minecraft 2026 水准”暗增范围。

本路线不依赖大模型、Agent Server 或另一个未合入 change。人、脚本与未来认知控制者都消费同一受约束世界能力。Headless/Browser 共享权威语义；输入、渲染、摄像机、音频仅在浏览器验收。Node Dedicated 产品已归档。

## 2. 术语：职责、能力与交付不是同一维度

| 名称          | 定义                                                         | 不是什么                                     |
| ------------- | ------------------------------------------------------------ | -------------------------------------------- |
| 小内核 Kernel | 世界身份、状态生命周期、调度、授权与提交等不可绕过的运行基础 | 包含全部默认玩法的万能 GameServer            |
| 基础服务      | 紧凑体素、空间、ECS 存储适配、物理接入等窄合同能力           | 必须全部允许模组热替换的插件                 |
| 模块 Module   | 引擎可识别、注册、调度、释放并被其他模块消费的能力单元       | 每个 helper；一条 Worker；天然独立 npm 包    |
| 标准机制库    | 第一方提供的标准模块集合，含默认实现和公开扩展策略           | 只有官方可以调用的特权实现                   |
| 模组 Pack     | 社区传播/交付单位，带 manifest，可包含任意数量模块和分面     | 每个包都必须是完整游戏                       |
| 模组 API      | 内核及模块的公开、版本化能力合同                             | 中间再运行一套世界；完整私有对象的重命名导出 |
| Playbook      | 满足玩法成立合同并占据唯一组合根位置的 Pack                  | 超级管理员；独立于模组体系的新格式           |
| Ruleset       | 世界/角色/区域等作用范围内的规则定义、组合与配置             | 另一个权威服务器或无限制事件总线             |

一个 Pack 可以只有光影/资源，也可以提供整个游戏。Playbook 可以是超大 Pack，也可以只是选择一组成熟模组并协调规则的薄层。模块遵守统一生命周期，只证明可注册；替换别人的模块还须满足其业务接口、版本、数据和失败语义。

## 3. 运行分层与依赖

```text
Playbook：锁定 Pack/模块 + 选择有效 Ruleset + 初始化玩法
    │
    ├─ 玩法/内容模块：配方、工具品质、生物规则、模式、生成组合
    ├─ 标准或自定义机制模块：物品/库存/动作/战斗/合成/需求
    │       └─ 通过公开合同消费彼此，不读取别人的内部状态
    └─ Web 表现分面：资源 / UI / render / 动画 / 音频
            ↑ 只读已提交投影与事实；向权威提交合法意图
小内核与基础服务：身份 / ECS基础 / 体素 / 调度 / 授权 / 事务 / 保存
```

这是逻辑职责，不是预定文件夹或包依赖图。当前 `packages/game-core` 同时容纳若干层，物理包名不自动使里面所有功能成为不可替换内核。边界先由 owner、公共 facade、负例测试确定，稳定职责簇出现后再拆包。

### 3.1 什么进入内核

判断规则：所有模块都必须遵守、不能由某种玩法绕过的运行保证进入内核；有多种合理实现、可以不存在或含玩法解释的能力优先进入标准库。

| 责任       | 内核/基础服务                                        | 标准模块或玩法                               |
| ---------- | ---------------------------------------------------- | -------------------------------------------- |
| 实体与组件 | 稳定 EntityId、生命周期、schema/codec 注册、存储适配 | Health、Needs、Inventory、Equipment 及其规则 |
| 体素与空间 | 紧凑数值存储、受控编辑、基础查询、版本化生成入口     | 方块内容、矿种、地形 provider、挖掘判定      |
| 物品       | 通用组件与版本化状态机制                             | 物品定义/实例/堆叠、库存、耐久、标签约定     |
| 动作与时间 | 逻辑时间、调度阶段、操作提交/回执基础                | 动作轨道、前后摇、连招、技能、冷却策略       |
| 物理       | 身体/空间接入及单一权威位置写入合同                  | 控制策略、飞行、击退、移动动作与玩法碰撞选择 |
| 规则与状态 | 授权执行、事务协调、已提交事实、检查点               | 伤害公式、PvP、合成、需求、工艺、世界法则    |
| 表现       | core 不持有 PlayCanvas、DOM、GPU 或音频对象          | 浏览器宿主、渲染/粒子/动画/光影模块和资源    |

小内核内部也可模块化，但普通模组只能消费公开 API，不能替换身份校验或读写内部数组；改变这些内部实现需修改引擎源码并交付新的引擎版本。核心开源不等于所有内部函数都是受兼容承诺保护的 API。

“不内置唯一战斗规则”不等于要求每位作者从头造战斗。作者可以复用标准战斗模块并替换伤害公式，也可以不加载它，基于空间、动作和事务能力实现不同机制。标准库提供可靠默认行为，不把它变成世界公理。

### 3.2 ECS 与数据组织

ECS 用于把能力从固定 player/npc 类型分支解放出来，不为了模块化把普通体素、每粒材料、骨骼和装饰粒子都实体化。角色共享位置/身体/生命/需求/库存等组件，控制来源是另一组件或适配；设备可有库存/过程而没有生命和 AI。

内部可回收 ECS ID 不对外暴露，也不进入存档/协议；组件迭代顺序不能无意决定争抢资源优先级。逐字段迁移，旧 facade 转发到新 owner，不维护两份长期可写状态。控制数据可以是对象，已测量数值热路径可以是 SoA；不宣称 ECS/SoA 自动带来性能收益。

## 4. 标准模块合同

引擎认识的是模块提供/需要的合同与声明，不是“战斗”这一预设名字。新模块至少声明适用于自己的内容：

- ID、接口/实现版本、来源 Pack、依赖/可选依赖、提供和需要的 capability。
- 状态 schema、默认值、单一 owner、只读投影、codec/迁移、删除/恢复行为。
- 资源、操作、参数/结果 schema、授权目标提取与真实执行器。
- 系统阶段、频率、逻辑时钟、读写依赖、初始化/执行顺序与稳定平局规则。
- 生命周期、资源释放、错误/冲突诊断，以及行为验收。

不要求纯资源包声明模拟 tick；不允许模拟系统自行创建权威 setInterval。自定义组件不会仅因注册就自动被物理、库存或 AI 理解，必须由消费该合同的系统赋予语义。Action 的工具描述也不能自动授予调用权限。

能力可选、扩展和替换分别定义：未选可选模块可以不存在；扩展通过公开 slots/hooks；替换独占 provider 需满足消费方合同并由组合根显式选择。加载顺序和“优先级更大”不能静默覆盖同名定义。

分层模拟是长期合同需求。模块声明当前支持的调度与精度模式；不支持粗粒度模拟时明确限制，不能盲目降频。当前不实现 LOD 或离线追赶，也不要求每个新模块先实现未来所有精度层。

## 5. Pack 的六个可选分面

| 分面      | 可以提供                               | 执行边界                                |
| --------- | -------------------------------------- | --------------------------------------- |
| code      | 模块、系统、组件、动作、规则和公开接口 | 纯逻辑/权威/client 入口分开             |
| data      | 物品、配方、标签、原型、规则与生成参数 | 加载时验证；不是任意代码执行            |
| resources | 模型、贴图、rig、动画、声音、图标      | 浏览器加载；权威只用必要的独立数据      |
| UI        | token、主题、槽位、面板和绑定          | 读取投影，交互提交合法操作              |
| render    | WebGL2 材质/天空/雾/光照 profile 等    | 宿主生命周期与预算；不公开私有 renderer |
| AI        | 算法策略、受限观察到意图适配           | 不取得另一套动作权限；模型不阻塞 tick   |

分面不是六层继承，也不强制六个文件。API 是跨分面的合同。模块可由 Pack 对外提供；普通内部函数不必被包装成模块或 Pack。

粒子和动画只能消费权威事实。若投射物会造成伤害，权威侧须有对应轨迹/碰撞与效果机制；不能靠客户端粒子碰撞或动画回调产生伤害。纯换肤不能暗改攻击窗口与距离。

## 6. API：低层开放，但受控提交

| API 家族                | 合同重点                                            |
| ----------------------- | --------------------------------------------------- |
| Registry / capabilities | namespace、来源、schema、版本、依赖校验、每世界冻结 |
| Query / observe         | 有界只读结果、来源/读取时点、权限过滤与失效         |
| Command / action        | 身份、幂等、前置条件、阶段/取消、拒绝与终态回执     |
| State / transaction     | 单 owner、候选/校验/提交、跨域一致性、失败无副作用  |
| Rules / hooks / events  | 可修饰提案与不可变事实分开、稳定顺序与重入限制      |
| Schedule                | 逻辑时间、阶段、频率、预算、过期异步结果拒绝        |
| Save / migrate          | 组件 codec、包版本、同 frontier、缺失依赖与迁移诊断 |
| Presentation            | 只读投影、句柄/资源释放、取消、去重与失效           |

这些是能力家族，不是一次实现全部功能的要求。只冻结经实际消费者验证的候选合同，后续版本化演进；不承诺任意未来玩法无需增加新通用原语。

### 6.1 批量编辑

`world.editBatch` 是示意名，应表示受控操作/事务入口，不表示公开 Chunk 数组。必须定义主体与模块来源、目标范围、批次上限、前置版本、原子性、失败、事件和回执。超大批次明确拒绝或声明非原子的分批操作，不能悄悄部分成功。

普通角色放置与规则模块生成建筑可以共用提交机制，但能力授予不同。模块处理角色请求时保留原始身份，不得借自己的权限使未授权角色完成操作。跨方块/库存/实体操作由已注册参与者形成候选并一起提交；不能宣称包括任意外部 I/O 的万能事务。

### 6.2 规则与事实

请求 → 身份/权限 → 玩法前置校验 → 动作执行与候选效果 → 规则修饰 → 不变量校验/提交 → 已发生事实。

提交前的命名规则可以允许、拒绝、修改合法提案；运行顺序、读取原始还是累积提案、独占替换都必须明确。接受动作不等于提前允许未来伤害，执行检查点仍校验规则与目标。

`world.listen` 是示意名，订阅的是公开、版本化、受保护的事件，不是任意内部函数或内存写入。提交后事件不可改写旧事实，只能排队新的正常操作；明确队列预算、释放、重入与循环限制。异步回调返回的候选需校验 epoch/revision 和输入身份，不能把已失效结果写回。

## 7. Ruleset：规则定义独立，运行权威唯一

模块提供规则定义及可配置参数，Playbook 选择组合，装配后形成版本化有效 Ruleset。Ruleset 可以在某个 Pack 内交付，不必单独一个包；它依赖模块 API，但不反向定义第二个引擎。

声明式参数如 PvP、死亡掉落，通过同一规则执行路径生效；代码扩展实现公式、校验和模式策略。命令只是获授权的调用入口，不跳过规则状态的版本和保存。可热改配置与需重启/迁移的代码/模块更换分别声明。

世界规则、角色模式和区域规则不能混为一个全局布尔表。生存/创造是本期验证模式，但引擎不硬编码“所有世界都必须有这两种模式”；模式切换涉及身体、库存、在途动作的处理，由玩法合同确定。

“解耦”指显式单向依赖、单一 owner 和稳定合同，而不是 Playbook、Ruleset 与模块互相完全不知道。

## 8. 合成例子：机制、交互和内容分离

物品/库存＋标签查询＋事务 → 合成匹配与消耗产出机制 → 工位/交互策略 → 配方与玩法内容。

- 新物品定义与新配方是两项注册；配方引用物品/tag，不暗中创建物品 schema。
- 背包无序合成、工作台3×3、摆放合成、点击转换可以共享事务基础，不必共享匹配器或 UI。
- 配方可声明条件、数量、实例消耗、产物/副产物；需要更复杂行为时通过代码提供标准模块，而不是无限堆特殊 JSON 字段。
- 满格、缺料、重复请求、工位被破坏、保存/恢复均有一致语义；不能先扣料再尝试产出。
- 一个玩法可以不加载默认 MC 类合成，其他模块通过明确 capability 使用替代 provider。

同理，战斗、需求、装备、行为、工艺都是领域积木。“挖掘、伤害”等名称不是内核不可替换概念。

## 9. Playbook、权限与完整性

一个可游玩世界有且只有一个 Playbook，满足 manifest、依赖闭合、初始化/恢复以及玩法所需控制/表现接入合同。可玩性由真实旅程验证，不能由一个签名或布尔字段证明。

Playbook 可以选择 provider、配置、规则顺序与许可覆盖；不能越过内核不变量、宿主权限、schema 兼容或迁移要求。引擎报告双方来源与冲突点，无法合法组合则拒绝；不承诺解决任意程序行为冲突。

包权限和角色权限不同：前者控制模块能使用的能力/资源，后者控制调用者能控制和观察什么。两者必须在同一权威路径落实，宿主绑定身份，模块不能靠标签/manifest 自授权限。已合并 #25 的授权模型是复用基础，而不是“角色权限全部完成”的证明。

首期不做第一方签发/认证；执行锁清单与实际包/资源内容的哈希校验。内容摘要验证一致性，不证明作者可信，也不抵抗包与清单一起被不可信来源替换。可信入口/分发链和恶意代码隔离在开放社区执行前另立合同；同 realm 的 API facade 和 Worker 不是恶意 JS 安全沙箱。

## 10. 装配、发布与恢复

生命周期：读锁清单 → 校验版本/摘要/依赖 → 注册与冲突检查 → 明确 provider/规则顺序 → 冻结定义 → 创建或恢复 → 挂载表现 → 运行 → checkpoint → 释放。

初始化不能在 import 时隐式修改世界。定义与状态分开，多个世界不能共用可变全局 registry。模拟模块不因一个 Pack 对应一个 Worker，所有权威操作仍由唯一 owner 提交。

发布固定引擎、Pack/模块、规则、资源与生成版本；存档记录演化状态并引用该发布身份。组件、库存、地形等在共同 frontier 冻结，不让各 mod 各存一个时刻。必需包缺失/坏摘要/不可迁移时在替换当前世界前拒绝，不静默删物品或把未知方块变空气。

首期启动加载、重启换包，不承诺任意热卸载。纯表现替换与改变规则/轨迹/生成是不同变更；引擎或规则升级需要显式迁移，不能后台改旧世界。

## 11. 第一期与长期路线

第一期：可组合玩法架构与第一方主世界 Playbook。迁出现有玩法，补齐基础探索、采集、合成/基础冶炼、库存/储物、食物/昼夜、生物战斗、建造、死亡/复活、保存及工具品质成长；生存/创造和替代机制样例验证合同。

具体内容级别、模式切换、生成/存档迁移和验收由[第一期 spec](../changes/2026-09-09-composable-overworld-playbook/spec.md)冻结，不用“完整主世界”暗指原版所有系统。复杂红石、多维度、现代整合包光影与内容全量、工业/策略/RPG 等均非本期。

基础玩法无特权后门＋差异样例通过，才将真实使用的 API 候选提升为稳定边界；不能只把目录搬走就宣布插件化完成。长期规划仍见[玩法路线](playbook-roadmap.md)，视觉上限参照另行建立。

## 12. 实施与验证原则

复用既有体素/事务/物理/动作/表现/Harness，在真实消费者推动下逐步抽取标准模块。通用 ECS 等优先核对成熟库，做锁版本准入，不因为文档说模块化就自行重写存储/渲染/调度引擎。库选择、拆包、私有函数签名都不是本文永久冻结的决定。

每次迁移保持单 owner、同宿主语义和可恢复行为；用公开 API 正反例、去默认模块样例、跨宿主保存、实际玩家输入验证。纯逻辑测试不能证明音画体验，性能没有受控证据就不声称提升。

本文是跨 change 的概念基线。具体生产变更继续按[开发治理](development-governance.md)做 spec、RED、精确审核、实现、GREEN、独立审阅和 PR；本轮讨论不豁免该门禁。
