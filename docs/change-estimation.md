# 大规模变更的工作量、AI 成本与预算

本规范由 2026-09-07 用户要求建立。它用于实施取舍、goal 预算建议和实际成本复盘，与[开发治理](development-governance.md)和[模型路由](collaboration-routing.md)一起使用；估算不代表实施或付费授权。

## 适用范围与登记时点

满足任一条件即视为大规模 change：传统工程工作量初估 ≥5 PD；Agent 连续完成时间初估 ≥24 小时；或涉及至少三个可独立验收的阶段且跨模块/运行时/部署边界。用户明确要求估算时不受大小限制。不要以拆小目录规避一个整体目标的成本登记。

实施前在 spec 加入「工作量与预算」并链接当前 change 的 `estimates.md`（简单表格也可直接写 spec）。初版、重大范围/模型/计费/实验矩阵变更、每个阶段结束、创建 goal 前和最终交付均更新。Delivered/Archived 历史不追溯补造数字；复用时估算新工作。纯文档等小变更可写 N/A 及原因。

## 双口径及最小字段

| 口径          | 必须记录                                                                                                                | 不能混用                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 传统工程量    | 按阶段的 PD 正常/保守范围，1 PD=8 小时熟悉项目的工程师有效工作；含设计、实施、联调、测试、返工和交付                    | 这是人力工作量，不能直接除以 24 得到 AI 日历时间，也不是雇佣报价                                 |
| AI 工作与时间 | 模型/effort/速度档/并发假设、正常工作单元、Agent 活跃工时、无人值守工具运行、关键路径、外部等待                         | 以 24h 不间断可用估算日历天，不能把所有并发 agent 工时相加当墙钟，也不能把长基准等待全算模型生成 |
| AI 消费       | 各模型未缓存输入、缓存输入、输出（含计费 reasoning）的估计及来源；分别换算 credits 与 API 美元，列工具/基础设施额外费用 | credits ≠ tokens；API 等价费用与订阅内的实际增量现金支出不同，二者不能重复相加                   |
| 当前额度      | 读取时间、每个 limit/window 的使用/剩余比例与 reset、余额及来源；本 change 的预测占比和可辨识性                         | 账户共享窗口不等于单任务预算，不同桶不可相加；reset credit 不是消费 credit                       |
| 预算          | 正常估计、保守规划值、选用基数、20% buffer、目标成本/时间上限、工具可执行单位                                           | 不把缓冲重复加到子项及总计；不能暗中扩大额度或换计量单位                                         |
| 实际与复盘    | 已耗、剩余预估、完工预估、偏差、返工原因与测量缺口                                                                      | unknown 不能写 0，未执行的估算不能写实测                                                         |

每项说明范围、依据日期与置信度；没有项目标定样本时使用明确假设的量级估算，保留敏感性分析。不得用固定“AI 是人类 N 倍快”换算全部工作。协调、重复上下文、重试、评审、验收和必要修复都要计入，不能只估第一次写代码。

## 计费与额度算法

费率在每次大变更/创建 goal 前从当前官方资料或明确账户合同核验，按模型和计费类别保存来源与快照日期，不把价格表写死为永久规则。credits 用[官方 credits 费率](https://learn.chatgpt.com/docs/pricing)，API 用[官方模型价格](https://developers.openai.com/api/docs/models/compare)。

对每个模型 m 分别登记未缓存输入 U、缓存输入 C、计费输出 O；credits 估算为 `Σ(U×rU + C×rC + O×rO) / 1,000,000`，API 等价美元用对应美元单价做同一求和。缓存输入若原日志包含在 input 总数中，先扣出以免重复计费。额外 cache-write、长上下文、速度档、工具调用、图像/视觉评审费率按该产品真实规则另算；effort 改变 token 量，不凭空给它编固定消费倍率。credits 与 API 各自查倍率，不能共用一个 multiplier。

如果采用单位任务法，要定义一个正常任务包含什么、预计多少次模型往返、模型构成、缓存比例与工时，再乘任务数；一个任务不是一次用户消息。首个代表阶段回填真实 usage/cost/elapsed 校准后重估。并发模型的费用相加，时间按资源和依赖图求关键路径；默认未授权并发时使用单个活动 agent 的时间口径，不以并行省时隐含派发授权。

只有存在同量纲的额度总量/剩余量，才计算 `本 change 预测量 / 剩余额度 ×100%`。只得到使用百分比时，记录当前剩余并把预测占比记 unknown；可在无其他任务、未跨 reset 的阶段采样百分点变化，报告精度、模型与窗口，再估剩余阶段。存在其他任务或四舍五入则不能当本 change 精确消耗。没有分母不能从 API 美元、credits 余额或订阅月费推导 included limit 容量。

## 20% 缓冲与 goal

默认建议预算 `B = ceil(1.2 × E)`，E 选经说明的保守剩余用量；同时展示正常值，避免隐去保守假设。整数 credits/token 向上取整，美元到分，时间到小时。每种单位分别计算；整体目标的重估使用「已耗 + 1.2×剩余估计」，不能忘记已耗或重新发放整个预算。已知的测试/返工在 E 内，20% 只作为额外不确定性缓冲；超出范围的需求重新估算。

**先检查当前 goal 工具的真实预算单位。** 本规范建立时 `create_goal` 仅接受 `token_budget`，没有 credits/USD/wall-clock 硬上限；因此 credits/USD 预算只能成为可观察的管理合同，不能声称平台已强制。需要 token 预算时单独估算工具实际统计的 token 口径并乘 1.2，验证缓存/reasoning/子 agent 是否计入。若口径未确认，标待校准，不把 credits 数填成 token。token 上限不能单独保证金钱上限，缓存命中率与模型改变都会影响价格。

仅用户明确要求创建 goal 才调用工具；只说未来用预算决策不代表现在创建。申请预算前给出可复核的估算版本、范围与单位。默认不自动购买 credits、兑换 reset、切换付费凭据或提高预算。正常估计耗尽时报告缓冲使用；预计完工将越过批准上限时提前保存可恢复状态并提出范围/预算取舍，未获调整则不开始会超限的新阶段。安全收尾不冒充功能完成。

## 24h 时间与验收记录

墙钟为关键路径上 Agent 工作和不可重叠的工具时间，再加明确外部等待；`连续天数 = 墙钟小时 / 24`。同时给无并发基线；若假设多 agent/多机器，说明授权、数量、共享采样设备和协调成本。审核等待、账号额度 reset、证书/网络故障可能延长现实交付，不能塞入 PD 或假装已包含在 24h 连续承诺里。

Delivery Snapshot 回填正常/保守预估与真实值；真实 credits、API 账单、token、账户百分点、Agent 工时、机器采样、墙钟分别注明可用性。新增规则本身由文档与算术核验；不要求给每份估算写复制其数字的测试，不把缺少精确计费数据变成无法继续已授权低风险设计的理由。
