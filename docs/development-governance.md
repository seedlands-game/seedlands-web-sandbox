# 开发治理与证据基线

本页保存跨 change 复用的准出规则；运行方式仍以 README 和 `package.json` 为准。

## 轻量 SDD

每个改变生产代码、产品行为、架构、配置或测试口径的需求，先建立 `changes/YYYY-MM-DD-kebab-name/spec.md`。它至少写清目标、范围/非目标、关键决定、Given/When/Then 行为、实施前测试设计、逐项证据、任务状态和 Delivery Snapshot。

大规模 change 还必须在实施前加入「工作量与预算」或链接本 change 的 `estimates.md`，遵守[双口径估算规范](change-estimation.md)：传统 PD 与 Agent 工时/24h 连续完成时间分别估算；分模型列 credits、API 等价费用、当前额度占比、置信度和保守值 ×120% 预算。范围/模型变化与阶段结束重估，Delivery Snapshot 回填实际和缺失证据；未知不能写 0，也不自动授权创建 goal 或支出。

简单且已澄清的需求走 **Agile**：短 spec、RED、实现、GREEN 和本地准出连续完成。安全、权限、持久化格式、世界生成/Chunk、渲染管线、公开契约、跨模块重构或不可逆数据走 **Breaking**：先写 spec 与用例，用户审核精确 SHA-256 后实施。目标或方案不清楚时走 **Exploration**：仅在 `/tmp` 或独立非生产位置试验，不导入产品，方向稳定后以新 spec 和新审核正式实现。

### 模糊需求澄清模式

模糊需求的目标不是尽快把用户说出的技术方案整理成 spec，而是以最低成本找到最值得验证的产品与工程路径。用户拥有产品意图和最终取舍权；用户提出的框架、架构、协议、性能手段或实现顺序默认是**候选假设**，不因来自用户就升级为事实或硬约束。只有用户明确声明不可改变，或仓库中已有仍然生效的决策合同，才把技术选择当作约束。

澄清记录至少分开以下内容，不能把它们压成一段“需求理解”：

| 类别               | 要回答的问题                                                   | 处理方式                                             |
| ------------------ | -------------------------------------------------------------- | ---------------------------------------------------- |
| 意图与成功体验     | 用户最终想让玩家、开发者或 Agent 得到什么？为什么现在做？      | 作为方案比较的核心，不因技术路线变化而丢失           |
| 长期愿景与当前阶段 | 这项需求服务哪条长期路线？下一个必须验证的里程碑是什么？       | 对照 `docs/living-world-alignment.md` 和真实项目状态 |
| 硬约束             | 安全、授权、兼容性、预算、时间、部署或已有合同中哪些不能改变？ | 标明来源；未确认的偏好不得伪装成约束                 |
| 技术假设           | 用户和智能体各自认为“必须这样做”“这样更快”的判断是什么？       | 逐条列为待证伪假设，记录证据与置信边界               |
| 未知项             | 哪个未知会真正改变选择？                                       | 优先消除决策价值最高的未知，不把所有细节都问完       |

澄清者必须承担技术判断责任：先读取当前源码、依赖、测试、历史决策和可复用能力，再核对候选项目或服务仍然有效的一手资料；对维护状态、许可证、生态兼容、接入面和退出成本有时效性的结论必须 live check。发现用户方案与意图、证据或项目不变量冲突时，应直接说明冲突、后果和更好的替代方案。不能只列选项让不熟悉该领域的用户承担未经分析的技术裁决，也不能用用户最初的措辞证明方案正确。调研深度必须与影响面和决策价值成比例：小型局部歧义只核对相关路径和真正可能改变决定的候选，不要求穷举仓库或市场；不适用的比较维度标为 `N/A` 并说明理由。

默认按以下顺序寻找路径：

1. 复用仓库已经存在且满足需求的能力；
2. 接入或薄封装成熟的社区库、标准、托管服务或工具；
3. 在成熟能力上做有界改造，保留清晰的替换与退出边界；
4. 只有前述候选不满足硬约束，或其接入、迁移、运行与维护总成本有证据高于自建时，才选择自建。

“造不如买”不是按 GitHub stars 或功能数量自动选型。按本次决策影响选取相关维度：硬约束覆盖、到首个可验证体验的时间、需要新增与删除的代码、与现有权威边界的适配、迁移和数据退出、运行与长期维护、许可证/供应链风险、失败后的可逆性；不相关项可以标为 `N/A`，但不能省略会改变推荐结论的成本。候选被排除时要写具体证据；无法实时验证的项目状态必须标为未知，不能据此声称社区方案不可用。已有自研代码既不是必须保留的沉没成本，也不是应被忽略的免费资产，比较的是从当前状态到下一验证目标的**剩余总成本**。

方案尚未稳定时，先用讨论、只读调研或最小可丢弃实验消除关键未知。实验必须围绕相同的代表性切片和成功口径，不用完整迁移、通用抽象层或更多底层建设替代产品验证。能由源码和一手资料回答的问题不先造原型；必须实测时才进入 Exploration 的隔离原型。稳定后的正式 spec 至少记录：推荐方案及理由、被否决候选与证据、最小纵向验证切片、自建例外理由（如适用）、失败/重开条件和仍未验证项。

以下行为视为澄清失败，必须继续调研或缩小问题：

- 将“我猜应该用 X”直接写成“需求必须使用 X”；
- 只论证用户提出的路线，不搜索现有能力和成熟候选；
- 用“更可控”“更先进”“以后可能需要”代替当前成本与验收证据；
- 为未来平台化预建抽象，却没有更快验证当前体验；
- 把一次启动、局部性能或内部测试当作产品意图已被验证；
- 为反驳自建而忽略已有资产、关键不变量或真实迁移成本。

完成澄清不等于得到用户对技术细节的附和。完成条件是：意图与技术假设已分离；现状和成熟候选已有足以支持决策的证据；推荐方案能解释为什么它是当前最低成本的有效验证路径；用户能够针对真实取舍作决定。若新证据推翻假设，回到本节重新比较，不维护先前方案的面子成本。

### 优化与技术选型实验

凡以更快、更省、更稳、更低延迟/资源/成本，或“某项技术更优”为采纳理由的 change，都必须把现状 A 与候选 B 做受控对照。这里的 A/B 是工程实验，不要求将未准入候选发布到线上或对真实用户分流。若改动只修复明确错误或实现新行为，按正确性/产品合同验收；没有对照证据时不得额外宣称它是优化。安全公告、许可证、平台弃用或硬兼容约束使旧 control 不可安全、不可合法或已不能运行时，可用一手公告和静态合同淘汰 A；这只证明硬约束，不证明 B 的运行时收益。

#### 先决定是否值得优化

开始实现前先证明至少命中一条边界：用户已经感知到的问题；产品 SLO/预算或回归门禁；开发、CI 或运营工作流的确定性预算；profile 中可重复的主要瓶颈；随已批准规模增长即将触发的硬上限。都未命中时不提前优化，记录观察项并停止。候选按“瓶颈贡献 × 发生频率 × 最终消费者影响”排序，再考虑实现、接入、维护和退出成本；优先处理当前短板，不因语言、框架、并行、SIMD、GPU 或协议更新而预设收益。

主指标优先选择最终消费者能感知或目标系统直接承担的结果，例如进入可玩时间、交互到可见反馈、frame/状态新鲜度尾延迟、错误率、下载/网络字节、真实资源成本，以及 CI 的准入成功率和等待时间。kernel 时间、函数耗时、draw call、分配和压缩率用于定位与解释；除非它本身就是预先声明的硬预算，否则不能单独替代端到端结果。

#### 每个候选的最小合同

每个分项在看结果前固定：待证伪假设、A 与 B、唯一主指标、必要次指标、正确性/权威/视觉/稳定性/资源否决项、最小有效收益、样本单位与样本数、执行顺序、统计量/估计量、通过判定式、停止线和失败后的恢复路径。A 与 B 一次只改变一个被测维度；若正确性前置无法拆开，必须把它声明为不可分割实验单元，不能把整组收益归给其中一个技术名词。

计时实验先用同配置 A/A 建立当前机器与观测器的噪声范围，再按预注册的平衡或交错顺序执行 A/B 或 AB/BA。记录 base source identity 及 A/B artifact/config hash；除预注册的实验轴外，两边保持相同的 corpus identity、seed、场景、输入、频率、并发、缓存、warmup、浏览器/运行时、设备和观测边界；无法一致的字段必须写明 `NOT_COMPARABLE`。性能采样通过[性能执行窗口](performance-execution.md)串行取得，不与构建、测试或其他 benchmark 竞争。

保留所有原始样本、启动/能力失败和负结果，不按结果删样本、换主指标、放宽阈值或重复运行挑选 GREEN。计时低于分辨率、缺少 GPU/GC/RSS/线上网络数据时写 `BELOW_TIMER_RESOLUTION`、`NOT_COLLECTED` 或 `UNSUPPORTED`，不填零，也不把 fallback 样本记到候选名下。确定性的 bytes、draw call、写入次数或分配计数可以作为分项精确 A/B，但仍要证明语义等价，并限制性能结论到该指标。

#### 从分项到采用

证据按层级解释，不能向上冒充：诊断 before/after 只能定位；microbenchmark 只能证明内核；含准备、复制、排队和回传的 component A/B 才能证明组件；目标路径的端到端 A/B 才能证明对产品用户、开发者、运营者或系统预算的最终收益；本机 headless 结果不能自动外推实体设备、WAN 或所有平台。技术选型还要把消息/数据语义、编码/布局、传输/执行环境和频率/并发拆成独立实验轴，使用相同 corpus 与消费边界；不能把少发字段、换算法或多线程的收益归给 codec、语言或网络协议。

计划共存且影响同一目标路径的分项通过后，必须以当前已接受栈为 control 做组合端到端 A/B。组合回归时按预注册的最大消融次数执行有界消融；没有单因素对照只能称关联警讯，不能指定唯一根因。只优化确定性硬预算且不与其他候选共存的分项，可以用 exact A/B 加语义和回归门禁单独准入，但不得扩张成未测的产品收益。主指标未通过预注册判定式、尾延迟/资源/正确性任一否决项失败、维护成本抵消收益时，默认保留更简单的 A。负结果、`NOT_RUN` 和 `ABANDONED` 都是有效交付；未采用的生产开关、依赖和死分支应移除，保留可复现实验、结论与重开条件。

优化通过只证明绑定 source、环境、负载和证据边界内的收益，不是永久豁免。后续改动若改变关键路径、功能集合、依赖、平台或基线身份，必须重跑相关 A/B；新增功能成本不能靠更新 baseline 隐藏，旧数据也不能重新归因给新提交。历史做法与反例见[本次优化实验回顾](../changes/2026-09-08-ambiguity-clarification-governance/optimization-retrospective.md)。

审核本身不自动授权超出合同的发布、其他外部写入、权限变更或删除。项目默认交接由本用户长期授权：验收后的 change 可将功能分支推送至已配置 `origin`，并以目标分支为 base 创建或更新 PR；用户指定 `local-only`、不发 PR 或其他范围时优先。不得自动合并或绕过分支保护。`Scope`、`Decisions`、`Behaviour`、`Test Design` 或 `Acceptance` 的实质变化会使原 hash 审核失效，必须重新审核。每次准出记录 docs baseline 是否更新：跨 change 的难重建规则更新 docs；只影响局部行为时写明不更新理由。

大规模 change 在派发前必须给出双口径估算：传统 PD，以及分模型 agent 工时、按 24 小时连续执行的关键路径、credits/API 等价和当前额度占比。估算包含上下文、协调、验收与返工，20% buffer 只计一次；无法取得的数字写 `unknown`，credits、token、API 价格和订阅额度不得混作同一单位。只有用户明确要求时才创建 goal。格式可参考[本次估算](../changes/2026-09-07-agent-routing-contracts/estimates.md)，但费率与额度必须按当时状态核对。

## E2E 生命周期

`tests/e2e/` 只放长期核心基线；`changes/<change>/e2e/` 和 `midscene/` 保存当次需求证据。`pnpm test:e2e`、`pnpm harness:e2e` 与 `pnpm harness` 只执行基线；当前需求由显式 change 路径运行。

- **Active**：合同和需求用例由当前 change 维护、显式执行。
- **Delivered**：用例随 spec 保留为当次证据，不承诺随未来 API 变化维护。
- **Archived**：spec 和用例一起冻结在 ZIP 中；复用时由新 change 重新定义预期。

需求用例进入长期基线前，必须有实施者之外的高智能模型独立评审，覆盖长期价值、重复度、确定性、成本与维护负担；当前项目路由为 Sol/xhigh，并在 spec 记录请求的模型/effort 与结论。缺少或不通过时 fail closed，继续保留在 change。基线提炼后的目标、旅程或成本发生实质变化时原评审失效；基线提炼后要去重，并在 Delivery Snapshot 区分当前保护和历史证据。

## 证据边界

每个 PR 的核心保护、GitHub hosted runner 能力、WebSocket/真实模型边界和 flaky 处理见[CI 测试边界](ci-testing.md)。

Vitest 证明纯逻辑、数据、算法和确定性不变量；Playwright 证明真实浏览器的可观察行为和输入；Midscene 证明视觉/语义旅程；手工检查只补充不能稳定自动化的体验项。一个验收项可需要多种证据，不能以一种替代另一种；不适用时写 `N/A` 和理由。

可程序化的 UI 行为优先 Playwright，视觉语义使用 Midscene；Midscene 在用户预算规划中可按近零增量成本估算，但真实运行仍可能依赖模型、密钥或服务，不能宣称免费。只有明确的单步诊断才直接使用 CDP/UI 调试，不把临时诊断代替可重复准出。

性能证据由 `seedlands-performance-validator`（默认 `Terra/high`）按[性能执行窗口](performance-execution.md)协调。采样命令必须持有机器级阻塞窗口；普通功能测试、等待时的负载、并发采样和未关联的历史结果都不构成当前性能证据。

`?harness=1` 只能通过生产 `World.edit()`、Store 或 streaming 路径构造确定状态，不替代真实 Pointer Lock 输入。`packages/game-core/src/world/**` 的 V8 行覆盖率不低于 80%；静态、构建、浏览器、Harness 和手工游玩要在 spec 中分别陈述真实结果。

## 交付

确认在明确功能分支后，只暂存本 change 的文件，使用语义化本地 commit；按已授权的 PR 交接推送、创建或更新 PR，并持续跟进本 change 相关 CI 与合并冲突。最新 HEAD 的必要 CI 通过、无合并冲突且 PR 为 `ready for review` 时可交棒；人类审核仍待完成，单个 `MERGEABLE` 字段不代表所有门禁通过。CI 失败只修复本 change 相关原因后复验；状态无变化时不重复通知。历史 evidence 不因目录/API 演进而静默改写。具体源码职责与可执行 ESLint 规则见[目录规范](repository-structure.md)。
